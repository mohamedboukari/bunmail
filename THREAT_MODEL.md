# BunMail: Threat Model

> Last reviewed: 2026-10-18

A self-hosted email service has a different threat surface than a SaaS one: there is no provider firewall in front of you, and you own the IP reputation, the database, the keys, and the abuse-response. This document walks the assets, the attackers we model against, the controls already in place, and the responsibilities that **stay with the operator**.

If you self-host BunMail, read the **Operator responsibilities** section. Some controls are not in the code and never will be.

## 1. Assets

| Asset | Why it matters |
|---|---|
| **API keys** (`api_keys.key_hash`) | Authenticate every API request. Compromise = full mail-send abuse. |
| **DKIM private keys** (`domains.dkim_private_key`, and `dkim_pending_private_key` during a key rotation, #250) | Sign outbound mail as a verified sender. Compromise = an attacker can forge mail from your domain that passes DKIM, until the key is rotated and its old record removed (#250). |
| **Email queue + history** (`emails`, `inbound_emails`) | Contains every recipient address, subject, and body that has flowed through the system. PII / commercial intelligence. |
| **Email tombstones** (`email_tombstones`, #34) | Post-purge audit snapshots: recipient address, Message-ID, subject (NOT body) for `TOMBSTONE_RETENTION_DAYS` days after the original was hard-deleted. Lower sensitivity than `emails` (no body) but higher *retention* (90d default vs 7d for trash). Set `TOMBSTONE_RETENTION_DAYS=1` to keep the bounce/complaint trace flow only for the freshest day of late feedback while minimising PII retention; the tombstone sweep runs every 6h. |
| **Sending IP reputation** | Earned over weeks. A few hours of abuse can take it months to recover. |
| **Webhook secrets** (`webhooks.secret`) | HMAC keys shared with the consumer. Compromise = forged webhook deliveries. |
| **Dashboard sessions** (`sessions.token_hash`, #216) | Opaque 256-bit cookie tokens; only their SHA-256 is stored, so a DB dump yields no usable cookie. A stolen live cookie = dashboard access until the real browser's next request reveals the copy (any superseded token, however old, revokes every session of the user, see §4) or the session is revoked. Superseded hashes are kept in `session_token_history` for the session's life. |
| **Dashboard passwords** (`user_credentials.secret_hash`, #215/#216) | argon2id hashes of account passwords (the owner and every invited account, #217). Compromise of the hash = offline guessing; of the password = dashboard login. |
| **Invitation tokens** (`user_tokens`, purpose `invite`, #217) | One-time link that creates an account with the invited role (`admin` or `member`). Only the SHA-256 hash is stored; the raw link exists in the invitation email or, when no system sender is usable, in the inviter's one-time reveal. Compromise before acceptance = the attacker creates the account under the invited address and role and is signed in. Valid `INVITE_EXPIRY_DAYS` (default 7). |
| **Password reset links** (`user_tokens`, purpose `password_reset`, #277) | One-time link, issued by an admin or the owner on the Users page, that sets a new password for one admin or member account and signs it in. Only the SHA-256 hash is stored; the raw link exists only in the issuer's one-time reveal (never emailed, logged or put in a URL). Compromise before use = the attacker takes over that account (and signs the real holder out everywhere). Valid 1 hour; one live link per account. |
| **Audit log** (`audit_events`, #221) | Who did what, when and from which IP, for every security-relevant action. Lets the owner and admins answer "was this me?" after an alert; an attacker who can edit it can hide a takeover. Holds account emails, key names, IPs and user agents (never passwords, tokens, keys or codes). Kept `AUDIT_LOG_RETENTION_DAYS` (default 365). |
| **Owner setup tokens** (`user_tokens`, purpose `owner_setup`, #215) | One-time link that sets the owner account's password. Only the SHA-256 hash is stored; the raw link exists once in the app log (or the operator's terminal after `reset-owner`). Compromise during the 24 h claim window = the attacker sets the owner password and is signed in to the dashboard. |

## 2. Attackers we model against

| Attacker | Goal | Realistic? |
|---|---|---|
| **Spam operator on the public internet** | Use BunMail as an open relay (inbound SMTP) or to send mail through stolen API keys. | Constant: assume always present. |
| **Internet scanner** | Find exposed dashboards, leaked `.env` files, vulnerable endpoints. | Constant. |
| **Compromised API consumer** | A leaked key sends mail from real domains. | Likely over time. |
| **Insider with DB read** (read-only replica access, leaked dump) | Harvest recipient lists, read inbound mail. **DKIM private keys (#23) and webhook signing secrets (#259) are AES-256-GCM encrypted at rest**: useless without `DKIM_ENCRYPTION_KEY` from `.env`, so a dump can neither sign mail nor forge webhook events. | Likely on careless backups. |
| **Privileged insider with DB write** | Forge mail history, grant their own API keys, exfiltrate. | Lower likelihood; full DB write effectively bypasses the app. |
| **Network adversary on egress path** | Strip TLS on outbound to recipients (downgrade attack). | Realistic on hostile networks; mostly irrelevant on cloud egress. |
| **Web XSS in dashboard** | Steal session cookie, send mail. | `@kitajs/html` escapes only children marked `safe` (it does **not** auto-escape): every interpolation of stored/user data carries `safe`. The DMARC pages were a gap (attacker-controlled aggregate-report fields) fixed in #131; a codebase-wide `xss-scan` gate runs in CI since #150 (blind spots closed in #229). |

We **do not** model nation-state attackers with side-channel access to the host, if they're on the box, the game is already over.

## 3. Trust boundaries

```
   ┌────────────────────────────────────────────────────────────────┐
   │  PUBLIC INTERNET                                               │
   │                                                                │
   │  ┌────────────────┐         ┌──────────────────────────────┐   │
   │  │ API consumer   │  TLS    │ Recipient MX servers         │   │
   │  │  (Bearer key)  │◄──────►│  (Gmail, Outlook, …)          │   │
   │  └───────┬────────┘         └──────────▲───────────────────┘   │
   └──────────┼─────────────────────────────┼───────────────────────┘
              │                             │ STARTTLS opportunistic
              ▼                             │
   ┌──────────────────────────────────────────────────────────────┐
   │  HOST (your VPS / bare metal)                                │
   │                                                              │
   │  ┌──────────────────────────┐    ┌────────────────────────┐  │
   │  │ Elysia: REST + dashboard │───►│ PostgreSQL             │  │
   │  └──────────┬───────────────┘    │  • API keys (hashed)   │  │
   │             │                    │  • DKIM keys (AES-GCM) │  │
   │             ▼                    │  • email queue + body  │  │
   │  ┌──────────────────────────┐    └────────────────────────┘  │
   │  │ smtp-server (inbound)    │                                │
   │  └──────────────────────────┘                                │
   └──────────────────────────────────────────────────────────────┘
```

The trust boundaries are: **public internet ↔ host** and **app process ↔ database**. Anything inside a single trust boundary is presumed cooperative; anything crossing one needs validation, authentication, or transport encryption.

**Shell access is the owner-recovery boundary (#215).** `src/db/reset-owner.ts` mints a fresh owner setup link and has no HTTP surface: it runs only as `docker compose exec app bun run src/db/reset-owner.ts` (or `bun run src/db/reset-owner.ts` on the host), and prints the link to the operator's terminal rather than the container log stream. Anyone with a shell on the host (or write access to `.env`) is already fully privileged (`DATABASE_URL`, `DKIM_ENCRYPTION_KEY`), so this grants nothing new; it is listed so nobody wires it to a web route. The same applies to `APP_BASE_URL`: someone who can edit it can point the logged link at their own host, which is accepted for the same reason.

## 4. What's mitigated in code today

### Authentication

- **API keys** are stored only as SHA-256 hashes (`api_keys.key_hash` is `UNIQUE`); the raw `bm_live_…` value is shown once at creation and never persisted. Bearer tokens are validated on every authenticated request via `src/middleware/auth.ts`: the lookup is cached on the `Request` (`WeakMap`) so we hash + query once per request.
- **One-time secret reveal (#132).** When the dashboard creates an API key or a webhook (or an invitation whose email did not go out, #217, or a password reset link, #277), the raw key / HMAC secret / link is **never placed in a URL**: URL query strings leak into browser history, reverse-proxy / CDN / access logs, and the `Referer` header. Instead the secret is stashed under an opaque 32-byte random token (`stashRevealSecret` in `src/pages/reveal-store.ts`), and only that token rides in the post-create redirect; the follow-up GET consumes it **once** (single-read, 60s TTL) and renders the secret. Each entry is **bound to its creator (#280)**: the kind of secret (an API-key token cannot be redeemed on the webhooks page, which members can open) and the user and session that created it (session ids survive token rotation). Any other presentation answers exactly like an unknown token, is logged at `warn` with IDs only, and does not consume the entry, so a leaked token is useless to anyone else and cannot be used to destroy the creator's one-time view. The reveal store is in-memory and per-process: on a multi-replica deploy a create on one replica and the GET on another would miss the token (operator revokes + recreates); a shared store is a separate concern (same caveat as the in-memory rate-limiter, #133).
- **Dashboard login (#216)** is email and password against `user_credentials` (`src/modules/users/services/login.service.ts`); the shared `DASHBOARD_PASSWORD` and the HMAC cookie keyed by `SESSION_SECRET` are gone. No account enumeration: unknown email, no password, disabled account, wrong password and over-long input all get the same `302` and `Invalid email or password.` (the reason is logged server-side only), and every branch runs exactly one argon2id verify (a missing account verifies against a dummy hash with the same parameters), so timing does not tell them apart. The login `POST` checks same-origin first (login CSRF), then the per-IP limiter (#109), before any database or argon2id work. A login revokes the session the browser already presented (no fixation, no stacking) and redirects only to the fixed `/dashboard`.
- **Dashboard sessions (#216)** are server-side rows in `sessions` (`src/modules/users/services/session.service.ts`). The cookie carries an opaque 256-bit token; only its SHA-256 is stored, and logs carry the `ses_` id, never the token or its hash. Cookies are `HttpOnly` + `SameSite=Lax`, plus **`Secure` in production** (#133). A session expires after 24 h idle and 7 days after login at the latest, computed on the Postgres clock. The guard shape-checks the cookie (a legacy `<ts>.<hmac>` value is cleared without a query), then does one indexed lookup that also requires an enabled user and `password`/`mfa` assurance, so a `pending` session (#220: password right, second factor not yet given) never opens a page; a database error answers `503` (fail closed). Logout deletes the row; owner setup completion and `reset-owner` delete every session of the owner. Sessions live in Postgres, so they hold across replicas and can be revoked one by one (the dashboard side of #183 and #185).
- **No timing-safe compare needed (#186).** There is no secret comparison in JavaScript left on the dashboard paths: the presented token is hashed and looked up through a unique index (an attacker controls the input to SHA-256, not a byte-by-byte compare against a secret), and argon2id verification is constant-time inside Bun. That is why the old `crypto.timingSafeEqual` check and its spy test were removed, not regressed. Each login mints a fresh token, so two logins never share a cookie.
- **Session token rotation and reuse detection (#216).** A session's token is replaced after 60 s of use: one conditional `UPDATE` keeps the old hash in `previous_token_hash` and slides the expiry (that write is the idle refresh), and the response carries the new cookie; when requests race, exactly one rotation wins. The replaced token is still accepted for 30 s (requests already in flight). Presented after that, two parties hold the session, so **every session of the user is revoked** and `Session token reuse detected: all sessions of the user revoked` is logged at `warn`. Every replaced hash is also kept in `session_token_history` until the session ends, so a token two or more rotations old (a thief keeping the stolen session active while the real browser idles) is caught the same way when the real browser comes back, including on the login and logout pages. Whichever side falls behind reveals the copy and ends every session. Limits: see §6.
- **Dashboard CSRF (#133).** Every state-mutating dashboard action is a POST behind the session guard; the guard rejects any POST whose `Origin`/`Referer` host isn't same-origin (**403**), a second layer beyond `SameSite=Lax`, and does so before a rotation, so a rejected request never carries a new token. A cross-site form-POST riding the operator's cookie carries the attacker's Origin and is refused. The public login, logout (#216), setup (#215) and invitation accept (#217) POSTs run the same check themselves.
- **Dashboard authorization (#222).** Behind the session guard, every protected route carries a minimum role as its own `beforeHandle` (`memberGuard`, `adminGuard`, `ownerGuard` in `src/pages/guards.tsx`; owner > admin > member). Members can read the dashboard, send, restore single messages, view or create templates, edit and delete the templates they created, and manage their own restricted API keys (#219, scoped in the services, see below); every domain, webhook and suppression change, the API key admin toggle, editing or deleting anyone else's templates (a member could otherwise rewrite production templates that API integrations send, DKIM-signed under the owner's domains), any trash (purged after `TRASH_RETENTION_DAYS`, so trashing is deletion with a delay), bulk and permanent deletes and empty trash need admin. The role comes from the same single query as the session (no stale role cached in the cookie), so a role change applies on the next request. A role too low gets `403` and a `warn` log with IDs only. Deny by default is enforced by a test: `dashboard-route-access.integration.test.ts` reads every route from the plugin and fails on any route missing from its table or not carrying the guard its entry names. `requireAssurance("mfa")` exists but is on no route: two-factor authentication (#220) is enforced by the login (a `pending` session until the code) and by the `REQUIRE_2FA` policy in the guard. Bodies and params are validated before the guard runs (an Elysia lifecycle property, as on the REST API), so an anonymous request with a malformed body gets `422` instead of `302`; it reveals only the public form schema.
- **Production guard:** the app refuses to start when `BUNMAIL_ENV=production` and `BUNMAIL_OWNER_EMAIL` is unset (`src/config.ts`; a malformed value is refused in every environment). The dashboard exposes unscoped read/write across all keys, and since #216 the owner account is its only login. `DASHBOARD_PASSWORD` and `SESSION_SECRET` no longer exist; a leftover value only logs a boot warning.
- **Owner bootstrap (#215).** On boot, `bootstrapOwner` (`src/modules/users/services/owner.service.ts`) creates the single owner for `BUNMAIL_OWNER_EMAIL` and mints a one-time setup token: 32 random bytes, stored only as its SHA-256 hash, valid 24 h, logged as a link once and only after the transaction commits. Every owner mutation (bootstrap, `reset-owner`, setup completion) runs under the Postgres advisory lock `bunmail:owner`, so replicas and crash loops can't create a second owner, and at most one live setup link exists (each mint revokes every open `owner_setup` token). After setup a changed `BUNMAIL_OWNER_EMAIL` only logs a warning: the env value never moves ownership and never promotes an existing account.
- **Setup page (`/dashboard/setup`, #215).** Public, so it carries its own controls: `GET` is read-only (link scanners and prefetchers can't spend the token), and only a successful `POST` consumes it, with a conditional `UPDATE ... used_at` in the same transaction as the password write, so two concurrent submissions can't both win. The `POST` runs the same-origin check itself, first (the guard's CSRF check doesn't cover public routes): a foreign `Origin`/`Referer`, or neither header, gets `403`. Cheap checks run first (token format, indexed hash lookup, password policy of 15 to 256 characters) so a bogus token never reaches argon2id. Missing, malformed, unknown, expired, used and revoked links get one identical `400` response (no oracle); a `token` over 128 characters fails schema validation with `422` before any lookup, which reveals nothing about stored tokens. Every setup response sends `Cache-Control: no-store`, `Referrer-Policy: strict-origin` (plus a meta tag: the origin only, never the token URL; not `no-referrer`, which makes browsers send `Origin: null` on the form POST), `X-Content-Type-Options: nosniff` and `X-Frame-Options: DENY`; success redirects to the fixed `/dashboard`, which removes the token from the address bar and allows no open redirect. Completion revokes the owner's other open tokens and, in the same locked transaction, deletes every session of the owner before opening the new one (#216), so no crash leaves an old session alive next to a new password. `reset-owner` deletes the owner's sessions as soon as it runs (a kill switch), and again at completion.

- **Invitations (#217).** Every account other than the owner is created by accepting an invitation. **Who may grant what** is checked in the service against the signed-in account's role (the owner grants admin or member, an admin grants member, nobody grants owner) on create, resend and revoke, so a crafted form gets `403`; the routes also carry `adminGuard`, and the database's `user_tokens_invite_check` refuses any `invite` row whose role is not `admin` or `member`, so no bug can mint an ownership link. An admin cannot replace or downgrade a live invitation of a role it cannot grant (an owner's admin invitation): refused with `pending_higher_role`, nothing changes. **Token:** 32 random bytes, stored only as SHA-256, valid `INVITE_EXPIRY_DAYS` (default 7, at most 90; `expires_at` set on the database clock), single use, live check on the database clock. **Inviter re-check at acceptance:** an invitation is acceptable only while `invited_by` names an existing, enabled account whose current role still grants the invitation's role, checked in the lookup and again inside the conditional spend `UPDATE`, so deleting, disabling or demoting an inviter kills the links it sent, even mid-acceptance. Every write for an address (create, resend, accept) runs under a per-address Postgres advisory lock, so at most one live link exists per address and an invitation is never issued next to an account created a moment earlier; an address that already has an account cannot be invited. **Delivery:** the link is emailed from `SYSTEM_MAIL_FROM` only when its domain is registered and DKIM-verified (signed with that key, one link, no tracking); otherwise, and always when `APP_BASE_URL` is not a usable `http(s)` URL (a `localhost` link is never emailed), it is shown once to the inviter through the one-time reveal store (bound to the inviter's user and session, 60 s), never in a URL, a flash message or a log; the pages that can show a one-time secret (Invitations, API Keys, Webhooks) are sent with `Cache-Control: no-store`. Names and invited addresses with control or format characters (`Cc`, `Cf`: bidi overrides, zero-width) are refused, and the email path logs errors by name and SQLSTATE only. **Accept page** (`/dashboard/invite`): the same controls as the setup page (read-only `GET`, same-origin first on `POST`, token shape and indexed lookup before the policy and before argon2id, one identical `400` for every dead link, `no-store`, `strict-origin`, `nosniff`, `DENY`); one transaction spends the token, creates the user, credential and session and revokes the address's other links; the browser's previous session is revoked. `email_verified_at` stays null (a hand-shared link proves nothing about the mailbox).
- **Account management (#218).** The Users page (`/dashboard/users`, `adminGuard`) changes roles, deactivates, reactivates and removes accounts, and transfers ownership. **Who may act on whom** is checked in `user-admin.service.ts` against the LIVE roles, read with `FOR NO KEY UPDATE` inside one transaction under the `bunmail:owner` advisory lock, never against the role the request's session carried: only the owner changes roles (member to admin or back, never to or from owner) and transfers ownership; deactivate, reactivate and remove follow the invitation rule (owner: any non-owner; admin: members only); nobody acts on their own account, and the owner is never demoted, deactivated or removed. A crafted request that no button leads to gets `403`; every outcome is logged (`info` applied, `warn` refused, IDs and roles, emails only redacted, never a password). Concurrent actions are serialized by the lock, so two admins acting at once or two racing transfers apply one after the other against committed state. **Revocation is immediate:** deactivation and removal delete every session of the account in the same transaction (its next request goes to the login page) and revoke the open invitations it issued; a demotion to member revokes its open invitations and applies on the next request (the role is read with the session). **Ownership transfer** goes to an active admin only, needs the owner's current password (argon2id verify, outside the lock, after the cheap rule checks), demotes the owner before promoting the target in one transaction (`users_single_owner` holds at every statement, exactly one owner after any interleaving), revokes the previous owner's open admin invitations and every open owner setup link (a `reset-owner` link for a former owner never comes back to life). **The transfer password check is throttled** with the login limits, per account (`transfer:user:<id>`) and per client IP (`transfer:ip:<ip>`): over budget it is refused before any argon2id work, each attempt is counted before the verify (a parallel burst cannot outrun it), and a completed transfer clears the counters; so a stolen owner session cannot guess the password faster than a login could. **Reactivation** deletes the account's sessions again, so a session created by a login racing the deactivation never comes back to life. **Removal** needs the account's email typed as confirmation; credentials, sessions and its own tokens cascade, `invited_by` on past invitations becomes `NULL`. **Keys of a deactivated or removed account (#219):** every active API key the account created is disabled in the same transaction (`creator_deactivated` / `creator_removed`; removal disables them before the delete clears their creator), so a leaver's keys stop at once over REST, SMTP submission and webhooks; reactivation does not re-enable them. **Sidebar:** members see no links to admin-only pages (Users, Invitations); the role comes from a request-scoped holder set by the session guard and fails closed. Display only: the routes enforce the roles.
- **Password reset links (#277).** Recovery for a non-owner who forgot their password, without email: an admin or the owner issues a one-time link from the Users page (`POST /dashboard/users/:id/reset-password`, `adminGuard`). **Who may reset whom** is the deactivation rule, checked in `user-admin.service.ts` on the live rows under the owner lock: the owner resets admins and members, an admin members; nobody their own account, never the owner (who recovers with `reset-owner`, shell access being that trust boundary), never a deactivated account. The token is 256-bit, stored only as its SHA-256, expires **1 hour** after issue on the database clock, and issuing a new link revokes the previous one. The link is **shown once** to the issuing user and session through the reveal store (kind `password_reset_link`); it is never emailed, logged, or put in a URL or flash. The public `/dashboard/reset` page mirrors the invitation accept page (auth-page headers, read-only `GET`, same-origin `POST` first, cheap checks before argon2id, one identical `400` page for every dead link). Using the link re-checks, in the spending `UPDATE` and under the owner lock, that the account is still enabled and that the issuer still exists, is enabled and may still manage the account's current role; deactivating the account or the issuer, demoting the issuer, promoting the account, or transferring ownership (the previous owner's links for admins and the new owner's own links) also revokes the open links, so none comes back to life when the change is undone within the hour. Success replaces the password, deletes **every** session of the account, revokes its other open tokens and the invitations and reset links it **issued** (whoever held the old password may have issued them; its legitimate pending invitations die too) and opens a fresh session in one transaction, and is logged at `warn` (`Password reset completed`, with the account, the issuer, the sessions revoked and the client IP). A completed reset **removes** the account's TOTP second factor and recovery codes (#220): it is the recovery path for a lost authenticator, so whoever holds a reset link also bypasses the account's 2FA (see §6). **Login racing a reset:** a login that verified the old password a moment before a reset committed would otherwise insert its session after the reset deleted every session, leaving the old password with a live session. Every session is therefore bound to the credential it was opened with (`sessions.credential_id`, FK ON DELETE CASCADE, migration `0019`): the reset's DELETE of the old credential cascades to its sessions, and the racing login's insert fails with a foreign-key violation, which the login route answers as an ordinary failed login. Sessions opened before `0019` are unbound (`NULL`) and are still removed by the reset's per-user revoke. An invalid reset POST is logged only at `debug`, so anonymous requests cannot flood the `warn` log.
- **Self-service password change (#279).** Every signed-in account, the owner included, changes its own password at `/dashboard/account/password` (`memberGuard`, behind the session guard, so a cross-origin POST gets `403`). It needs the current password: a stolen session alone cannot set a new one. Guessing that password through the form is throttled like a login: the login limiter's settings (`DASHBOARD_LOGIN_RATE_LIMIT_*`) under keys of its own, per account (`password:user:<id>`) and per client IP (`password:ip:<ip>`, IPv6 by `/64`); over budget is a `429` before any argon2id work, each attempt is counted before the single argon2id verify (a parallel burst cannot run more verifies than the budget), and a wrong password is not given back. The new password follows the owner setup policy (15 to 256 characters, confirmed, different from the current one), checked before any argon2id work. Success **signs out everywhere** in one transaction under the owner lock: every session of the account is deleted, the `password` credential replaced (its `credential_id` cascade is a second path to the sessions bound to it), the account's open reset links revoked, and a fresh session bound to the new credential issued to this browser only; a session thief is cut off the moment the real user changes the password. The current password is verified outside the lock and the credential re-checked inside it (same row, same hash, `FOR UPDATE`), so an admin-issued reset completed in between wins and the change is refused. Logged at `warn` (`Password changed`, `Password change refused` with a reason), never a password or a token.
- **Active sessions: see and sign out your own devices (#281).** Every signed-in account, the owner included, lists its own live sessions at `/dashboard/account/sessions` (device from the user agent, IP, approximate location, signed in, last active, this device marked) and signs out one of them or every other one (`memberGuard`, behind the session guard, so a cross-origin POST gets `403`). A user who spots a device they do not recognize cuts it off at once, without waiting for reuse detection or the 7-day cap. Only the account's own sessions: the delete is scoped to the signed-in user in SQL (`WHERE id = $id AND user_id = $userId`), so another account's session id, or an unknown one, changes nothing (`404`); other accounts' sessions stay on the Users page (deactivation, #218). The list never carries a token or a hash, and every stored value (user agent, IP, location) is escaped. Every sign-out is logged at `warn` (`Session revoked by its user`, `Other sessions revoked by their user`).
- **Approximate session locations are opt-in, and private by default (#281).** Off unless the operator configures a source. `GEOIP_DB_PATH` reads an offline DB-IP Lite or GeoLite2 `.mmdb` file: no third party sees any address. The online option (`GEOIP_PROVIDER=ipinfo` with `GEOIP_API_TOKEN`) **sends every sign-in IP address to ipinfo.io**, a privacy trade-off for the operator to weigh (documented as such); it uses HTTPS only, refuses redirects, times out after 3 seconds, caps the answer at 16 KiB and reads the JSON field by field, and the token never reaches a log line. Private, loopback and link-local addresses are never looked up. The lookup runs in the background after the session is committed, so a slow or failing source never delays or fails a sign-in (failures log a `warn`). A missing or corrupt `.mmdb` file logs one `warn` and leaves location off; a bad combination of variables refuses to boot. The location is approximate (a VPN shows its own) and is shown as such: it is a hint for the user, never an access-control input.
- **Email alert on sign-in from a new device (#282).** A password login (`POST /dashboard/login` only) from a browser the account has not used in the last 30 days emails the account "New sign-in to your BunMail account" from `SYSTEM_MAIL_FROM` (DKIM-signed, never unsigned), so a stolen password used from the attacker's own browser is noticed by the account holder. The browser is recognized by the `bm_device` cookie (32 random bytes, `HttpOnly; SameSite=Lax; Path=/dashboard`, `Secure` in production, 400 days), **not a credential**: no route accepts it for anything, it opens no session and skips no check; only its SHA-256 is stored (`user_devices.device_hash`), so a DB dump yields no cookie value. A malformed or oversized value is treated as absent. **The alert contains no links of any kind** (no URL, no token, no button, no tracking): a forwarded or leaked alert cannot act on the account, and users are not trained to click links in security mail; it tells them to sign in themselves and use Account > Active sessions > Sign out all other devices, change the password and tell an administrator. Every dynamic value is escaped in the HTML part and flattened in the text part, and the IP shown is only a valid IP literal. **What an attacker learns** from a leaked alert: the masked account address (`m***@example.com`), the browser and OS label, the sign-in IP, an approximate location and the time; nothing that signs in. The check runs in the background after the login response is decided, so it never delays a login or acts as a timing oracle on the password check, and a failing send or database error only logs a `warn`. Without a usable sender nothing is sent and the event is logged at `info` (`New-device sign-in`). Rows go with the account and are swept after 400 days unseen.
- **TOTP two-factor authentication (#220).** Any account can add a second factor: a time-based code (RFC 6238, HMAC-SHA1, 6 digits, 30 s) from an authenticator app, implemented on Node's `crypto` with no dependency (the QR code matrix comes from `uqr`, pinned, no dependencies; the SVG is built from its integers, so the `otpauth://` URI never reaches the page). **What it mitigates:** a stolen, phished, reused or guessed password alone no longer opens the dashboard for an account with 2FA, which is the main path to the owner's unscoped read/write and DKIM-signed sending. After the password the session is `pending` (10 minutes, admitted by no protected route); a valid code turns it into an `mfa` session with a fresh token (the pending token dies, so a planted or leaked pending cookie is worthless after the step). **Replay:** a code is accepted once; the last accepted time step is stored in `user_credentials.counter` with a compare-and-swap in the transaction that accepts the code, so two concurrent submissions of one code cannot both pass, and a code seen over a shoulder or in a phishing proxy's log cannot be reused. **Guessing:** every code check is budgeted with fixed numbers (5 failures per 15 minutes per key, always on, independent of `DASHBOARD_LOGIN_RATE_LIMIT_*`, whose values are now validated at boot), counted before the check so a parallel burst cannot exceed the budget. The login step spends `totp:user:<id>` and `totp:ip:<bucket>`; once spent the pending session is revoked and the account is emailed (once per window). Checks inside a session (disable, regenerate) spend `totp:session:<id>` and the address key, never the account key, so a stolen session cannot lock the real user's sign-in; once its own budget is spent that session is revoked. **Storage:** the secret is encrypted at rest with `DKIM_ENCRYPTION_KEY` (AES-256-GCM, like DKIM keys and webhook secrets: it must be readable to check codes, so it cannot be hashed); an enrolment in progress is kept encrypted on its own session row; recovery codes (ten, 80 random bits each, single use) are stored only as SHA-256. **Re-authentication:** starting an enrolment needs the current password (the password change's budget, one argon2id verify), and the pending secret is written only after it, so a stolen session cookie alone cannot turn 2FA on to sign the owner's other devices out and lock them behind a code only the thief has. Confirming 2FA signs out every other session of the account (they were opened with the password alone), and the guard admits a `password`-level session only while the account has no second factor, so a login that raced the confirmation keeps nothing. Disabling needs the password and a code (and an account without 2FA gets that answer before any password check, so the form is no password oracle); regenerating recovery codes needs an app code. **Security emails** (no links, DKIM-signed, from `SYSTEM_MAIL_FROM`, never blocking the action) tell the account when 2FA is turned on or off, when recovery codes are replaced, when a reset or `reset-owner` link removed it, and when its login code budget ran out after a correct password. `REQUIRE_2FA` (`owner`, `admin`) makes it mandatory: an account it covers without 2FA can open only its Two-factor page. Logs carry IDs and reasons only, never a secret, code, recovery code or URI.

### Inbound SMTP open-relay defences

Spam protection runs in four layers (`src/modules/inbound/services/smtp-receiver.service.ts`):

1. **Per-IP connection rate limiting**: sliding window, 10 connections / 60 s by default.
2. **DNSBL check**: Spamhaus ZEN by default. Listed IPs get SMTP 554 before they can issue `MAIL FROM`.
3. **Recipient domain validation**: RCPT TO is rejected with SMTP 550 unless the recipient's domain is registered in BunMail's `domains` table. This is the primary anti-relay control.
4. **Envelope + stream hardening** (#18):
   - SMTP `SIZE` extension caps messages at 10 MB; the `onData` stream re-counts bytes and aborts with SMTP 552 if a non-conforming client tries to overflow.
   - `RCPT TO` is rejected with SMTP 452 once 50 recipients are accepted in one transaction.
   - `MAIL FROM` is shape-validated; malformed envelopes get SMTP 553. Empty sender (`<>`) is preserved for legitimate DSN bounces.

All four layers **fail open** on internal errors (DNS timeout, DB unreachable) so legitimate mail isn't dropped on infrastructure hiccups.

**Threading identifiers (#192).** The `Message-ID`, `In-Reply-To` and `References` of received mail are attacker-controlled and are stored, reused in dashboard replies and used to link a reply to our own outbound mail. Only syntactically valid msg-ids are kept (`<id-left@id-right>`, printable ASCII without spaces, at most 250 characters each); comments, junk and anything with CR, LF or NUL are dropped, chains are capped to 20 ids, and extraction is one linear pass (`src/modules/inbound/services/threading.ts`). A dashboard reply never splices inbound text into headers: the form posts only the inbound email's id, the server re-parses the stored ids, builds `In-Reply-To` / `References` (capped to 998 characters) and passes them through the custom-header rules (#177). The reply link (`inbound_emails.in_reply_to_email_id`) counts only when the matched email's sender domain is one of the envelope `RCPT TO` domains (never the `To:` header), so a forged `References` cannot tie one tenant's inbound mail to another tenant's outbound mail. **Residual:** anyone who knows a Message-ID of ours on a domain (every recipient of that email does) can make a message to that domain show as a reply to it; the link is informational and shown only to dashboard users, who can already see every email.

**DMARC report parse hardening (#129).** A message that looks like a DMARC aggregate report is decompressed + XML-parsed on the (unauthenticated) inbound path. Both steps are bounded so one crafted email can't take the receiver down: decompression uses fflate's **streaming** `Gunzip`/`Unzip` fed in slices and **aborts past a 25 MB output cap** (a ~1000:1 gzip bomb would otherwise OOM the process); XML parsing runs with `processEntities: false` and rejects any `<!DOCTYPE` (billion-laughs CPU bomb). On any of these the report is dropped and normal inbound storage takes over. See `src/modules/dmarc-reports/services/dmarc-parser.service.ts`.

### SMTP submission (authenticated relay, #120)

The submission server (`src/modules/smtp-submission/services/smtp-submission.service.ts`, opt-in via `SMTP_SUBMISSION_ENABLED`) is a **deliberate relay** for authenticated clients: apps send *through* BunMail to arbitrary recipients. It is a different trust model from the inbound receiver, so its anti-abuse controls differ:

1. **AUTH is the anti-relay control.** `AUTH` is mandatory (`authOptional: false`); the password is treated as a BunMail API key (SHA-256 hashed → `findByHash`, must be active). Unauthenticated clients can't send at all, so, unlike the inbound receiver, recipient domains are intentionally *not* restricted.
2. **Per-IP failed-AUTH throttle.** Because the password is an API key, failed AUTHs are counted per IP (default 10 / 900 s) and locked out with SMTP `454` before the key is checked: blunts online key brute-forcing. Failures expire only with their window; a success does not clear them (#190), so one valid key cannot reset the count between guesses at others. The counter is per replica (#185).
3. **Per-IP connection rate limiting**: sliding window (default 30 / 60 s).
4. **Envelope hardening**: 10 MB `SIZE` cap (SMTP 552 on overflow) and a 50-recipient-per-transaction cap (SMTP 452). Delivery is the envelope only: `To`/`Cc` header addresses that were not sent in `RCPT TO` are dropped, so a long `To:` header cannot fan one submission out past the cap or the daily quota.
5. **Reuses the outbound gates.** Submitted messages go through `createEmail`, so the per-API-key **suppression** gate and the production **registered-sender-domain** requirement apply exactly as they do for REST sends (rejections surface as SMTP `550`).
6. **Header relay is an allowlist (#177).** Only `In-Reply-To`, `References` and `X-*` are copied from the submitted message, through the custom-header rules below (`X-BunMail-*` is reserved); a header that fails is dropped with a `warn` naming it, never its value. `Received`, `Content-*`, `List-Unsubscribe`, `DKIM-Signature` and the rest are rebuilt by BunMail, never copied.

**Credential-in-transit risk.** With no TLS configured, `allowInsecureAuth` permits the API key to travel in plaintext: acceptable only on a trusted network (same host / private Docker network). Operators exposing submission more broadly must set `SMTP_SUBMISSION_TLS_CERT`/`_KEY` (STARTTLS) and firewall port 587 to known clients. This is called out as an operator responsibility in §5.

### Sender authorization / anti-spoofing (#126)

Because outbound mail is DKIM-signed by its sender domain, an API key that can set an arbitrary `From` can send a **fully-authenticated impersonation** (e.g. a dev key sending as `ceo@company.com`). Mitigation: each key has an **allowed-senders allowlist** (`api_keys.allowed_senders`). When non-empty, the `createEmail` gate rejects any send whose `From` isn't on the list: **403 `UNAUTHORIZED_SENDER`** (REST) / **SMTP 550** (submission), before anything is queued. Enforced once in `createEmail`, so it covers the REST API and the SMTP submission server identically. Editable via `PATCH /api/v1/api-keys/:id` or the dashboard.

**API keys belong to users (#219).** Every key records the dashboard user it belongs to (`api_keys.created_by_user_id`; REST-created keys inherit the calling key's user; NULL = the owner, legacy keys are assigned to the owner at boot). A member manages only its own keys (another's answers "not found", so its existence does not leak) and only restricted ones: `isAdmin` on its create form is ignored server-side and the admin toggle is admin-only. Deactivating or removing a user disables its keys; reactivating does not re-enable them. Keys never move on an ownership transfer, so account actions on a former owner still reach its keys. Promotion to admin is a single conditional `UPDATE` that requires the key's creator to be an active admin or the owner (or no creator), so it cannot race a demotion. Key creation reads the creator's row `FOR SHARE` (conflicting with the account actions' row locks), refuses a deactivated creator and grants admin only from the creator's live role; the auth middleware and SMTP lookup reject a key whose creator is deactivated. Dashboard template and webhook creates use the user's own key, and member-facing key lists (send, emails and suppressions filters, inbound reply) are scoped to the member's keys. Demoting an admin to member makes every admin key it created restricted in the same transaction (the keys stay active for sending), so a member never holds a management-plane key; promotion restores none. On the dashboard send page a member can pick and submit only its own keys: any other key id, an admin's or the owner's included, is refused like a missing key and nothing is sent.

**Upgrade note (#219).** Keys created before #219 are attributed to the owner. After inviting other accounts, rotate any admin key that was shared with them: demoting, deactivating or removing an account only reaches the keys that account created.

**Key trust model (#130).** API keys are **admin** or **restricted** (`api_keys.is_admin`). Restricted keys are send-only + own-data; the **management plane** (`/api/v1/api-keys`, `/api/v1/domains`, `/api/v1/inbound`, `/api/v1/dmarc-reports`) is admin-only (`adminMiddleware` → `403 ADMIN_REQUIRED`). This is what makes the allowed-senders boundary real: a restricted key can no longer clear its own `allowedSenders`, read others' inbound, delete domains, or mint keys. `is_admin` is operator-set only (dashboard + seed), never via a REST DTO, so an API key can't self-escalate. Existing keys migrated to admin on upgrade: **demote any key handed to a less-trusted party.**

**Residual (operator responsibility):** the allowlist is **opt-in**: a restricted key with an *empty* list can still send as any address on any *registered* domain (BunMail has no per-key domain ownership; that's a deliberate deferral, since one domain is often shared by several keys). So: set `allowedSenders` on any restricted key you hand out. An **admin** key is a full operator credential: treat it like the dashboard owner password.

### Outbound delivery

- **DKIM signing** uses per-domain RSA-2048 keys generated at registration time. The private half is **encrypted at rest with AES-256-GCM** using `DKIM_ENCRYPTION_KEY` (#23), see `SECURITY.md` for format, generation, and rotation. The public half stays plaintext (it's published in DNS). **A compromised DKIM key can be rotated without downtime (#250):** an admin starts a rotation (a new key under a dated selector `bm<YYYYMMDD>`, pending), publishes its record next to the current one, and completes it; BunMail switches only after the new record resolves with the new key, mail is never unsigned in between, and the old private key is dropped at the switch, so BunMail never signs with it again. Before #250 the only way out of a leaked key was deleting and re-adding the domain, with mail unsigned or failing DKIM until the new record propagated. **Residual:** a stolen key keeps verifying for as long as its old TXT record stays published; the operator removes it (the advice is 7 days after the switch, sooner for a key known to be leaked, see SECURITY.md, DKIM key rotation). Rotation is admin-only (admin API key, `adminGuard`), audited with the selector only, and the API never returns a private key, active or pending.
- **Outbound SSRF guard on MX hosts.** Recipient domains are chosen by API callers, and anyone can publish an MX record pointing at a private address, so connecting to the MX name would let any key aim the server's port-25 connections at its internal network (and read connection errors back through `lastError`). The mailer resolves each MX host itself (`src/modules/emails/services/mx-address.ts`), refuses if **any** address is private/loopback/link-local/ULA/CGNAT/metadata (same ranges as the webhook guard), refuses a null MX, and connects to a checked address with the MX name as TLS SNI, so the DNS answer cannot change between check and connect. Every address goes through this check (#250): each MX host tried in failover (at most 5 hosts and 2 addresses per host per attempt), and the recipient domain's own A/AAAA records when it has no MX (the implicit MX, which otherwise would let a caller aim delivery at a private address with a plain A record). A refused host is skipped, never connected to. IPv4 is preferred, as nodemailer did: a host with an IPv4 address is never reached over IPv6. The refusal message never includes the resolved address. `MAIL_ALLOW_PRIVATE_MX=true` turns the check off for operators who deliver to an internal mail server on purpose.
- **Opportunistic STARTTLS** (#21, #250): every recipient MX that advertises STARTTLS is upgraded to TLS, at **TLS 1.2 or later** (`tls.minVersion`; a peer offering only older versions fails the handshake and the email is retried, never bounced). Receivers without STARTTLS stay in plaintext. Each delivery-state entry records whether its latest session used `starttls` or `plaintext` (#250), read from Nodemailer's own connection events and counted as encrypted only once an EHLO reply came back over TLS; the API returns it in `deliveryState`, and the email detail page badges a plaintext delivery. **Residual:** TLS stays opportunistic and certificates are not verified (no MTA-STS or DANE yet, #250), so an on-path attacker can strip the STARTTLS offer and downgrade a session to plaintext, or intercept it with any certificate. A stripped session is now visible as `plaintext`; an intercepted one is not.
- **Body size cap** (#26): `html` and `text` are validated at the DTO layer at 5 MB each: oversize bodies return `422` instead of pushing into the queue and crashing the transport on retry.
- **Request size and pre-auth handling.** Bodies are parsed and validated before the auth hooks run, so the server caps them at 12 MB (`maxRequestBodySize`, Bun rejects larger ones with `413` before reading; its default is 128 MB). Validation failures return `422 VALIDATION_ERROR` with paths and fixed messages only, never the submitted values, and are not logged as server errors (they used to fall through to the 500 path, which logged the whole request body). Templates are capped at 5 MB per body and 100 declared variables; a send passes at most 100 variables of up to 100 KB; rendering stops with `422` once a body would pass 5 MB or the subject 500 characters, so variables cannot amplify a template into a huge string.
- **Custom header injection (#177).** `POST /api/v1/emails/send` accepts a `headers` map, a header-injection surface. One pure rule set (`src/modules/emails/services/custom-headers.ts`) runs in `createEmail` for every ingress, and again in the mailer before a stored set reaches Nodemailer: names must be RFC 5322 field names (printable ASCII, no `:`, 1 to 64 characters); values must not contain CR, LF, NUL or any other control character except HTAB (C1 controls and U+2028/U+2029 too), at most 998 characters; at most 20 headers and 8 KB in total; no case-insensitive duplicates. **Reserved names are refused in any case** so a caller cannot override what the allowed-senders gate (#126), DKIM and the unsubscribe headers rely on: `From`, `Sender`, `To`, `Cc`, `Bcc`, `Reply-To`, `Subject`, `Date`, `Message-ID`, `Return-Path`, `Received`, `DKIM-Signature`, `Authentication-Results`, `Received-SPF`, `MIME-Version`, `List-Unsubscribe`, `List-Unsubscribe-Post`, `List-Id`, `Feedback-ID`, `Precedence`, `Auto-Submitted`, and the prefixes `Content-`, `ARC-`, `X-BunMail-`. Refusals are `422 VALIDATION_ERROR` (syntax, at the DTO) or `422 INVALID_CUSTOM_HEADER` (SMTP `550`), before anything is queued; messages and logs carry the header name (only when it is a valid name) and never the value. The mailer's second pass also stops a row written outside `createEmail` from replacing `Message-ID` or `List-Unsubscribe`, and BunMail's own headers are set after the custom ones. **Residual:** `X-*` headers are not in the DKIM-signed header list, so a relay could alter them without breaking the signature (`In-Reply-To` and `References` are signed).
- **Idempotency keys (#188).** An optional `Idempotency-Key` header on `POST /api/v1/emails/send` lets a client retry after a timeout without sending twice. Keys are **scoped to the calling API key** (unique on `(api_key_id, key)`), so two tenants choosing the same key never collide, and one tenant can neither replay nor probe another's stored response. The same key with another body is refused (`422 IDEMPOTENCY_KEY_REUSED`, comparing a SHA-256 of the canonical body) instead of silently answering with an unrelated email. The key is claimed with `INSERT ... ON CONFLICT` in the transaction that inserts the email, so concurrent duplicates yield exactly one email and no 500. The key value is never logged (only its length, at `debug`) and never echoed in errors. **No message content in the snapshot:** each key stores its first response without `subject`, `html`, `text` and custom `headers` (ids, addresses, status, timestamps and warnings only) for `IDEMPOTENCY_KEY_TTL_HOURS` (default 24, at most 168). A replay fills the content from the live email with one read scoped to the same API key and excluding trash; once the email is trashed or purged the replay returns the original ids and status with those fields `null`, so deleting an email removes its content everywhere. Expired rows are purged. A replay counts toward the per-key rate limit like any request.
- **Fair queue claiming (#258).** Each claimed batch of the send queue and of the webhook delivery worker is shared across API keys round-robin, so one key with a large backlog (or a receiver that is down and collecting retries) cannot delay other keys' mail or events. Combined with the in-flight cap (#176) and the bounded SMTP sessions (#250), a key can slow only its own share.
- **Queue isolation:** trashed and soft-deleted rows are excluded from the queue selector (`src/modules/emails/services/queue.service.ts`) so a deletion mid-flight cancels the send.
- **Suppression list** (#25): a per-API-key gate runs at `createEmail` before any insert / queue / SMTP work. Suppressed recipients return HTTP 422 with `code: "RECIPIENT_SUPPRESSED"` and never reach the wire. Address normalisation (case-fold, trim) prevents trivial bypasses.
- **Bounce → suppression chain** (#24, #236): when the inbound SMTP receives a Delivery Status Notification, the bounce module parses it (RFC 3464 + heuristic-gated regex fallback) and persists a per-API-key suppression. Hard bounces (5.x.x) become permanent suppressions; soft bounces (4.x.x) become 24-hour windowed suppressions and escalate to permanent on a second soft bounce within the window. A bounce never weakens a suppression (#191): it only rewrites a temporary row, so a late or forged DSN cannot turn a complaint, unsubscribe or manual entry into a 24-hour one that lapses. **Co-recipient bounce forgery: mitigated by #236.** DSNs are unauthenticated and the Message-ID is visible to every recipient, so linking by Message-ID (before #236, even with the check that the bounced address was a recipient of that email) let a recipient forge a bounce for a co-recipient and get that address suppressed under the sender's key. With `SMTP_ENABLED=true` (the only setup where DSNs reach BunMail), for a sender domain whose MX points at this server, each recipient is now sent in its own SMTP transaction whose envelope sender is a signed return path, `b+<email id hex>.<recipient index>.<MAC>@<sender domain>` (HMAC-SHA256 truncated to 96 bits, key derived by HKDF from `DKIM_ENCRYPTION_KEY` under its own label, lowercase hex so case folding cannot break it). The receiver refuses at `RCPT TO` (`550`) any `b+` address that does not verify against its email row (MAC, recipient index, sender domain, constant-time compare); a DSN to a verified address applies to exactly that email and recipient, whatever its body names, and a DSN to any other address has no effect. Co-recipients never see each other's return path, because each transaction carries only its own. Non-DSN mail to a return path (auto-replies) is dropped and never stored. **Residual:** whoever can read a recipient's own return path (the recipient, whose delivered copy usually shows it in `Return-Path:`, their mailbox provider, anyone they forward the message to) can bounce that one recipient, which equals that recipient's own provider bouncing it. Rotating `DKIM_ENCRYPTION_KEY` invalidates outstanding return paths (late DSNs for older mail are ignored; inline `5xx` at send time still suppress). The parser runs on every inbound message, so it is kept linear-time and covered by bounded-time tests.
- **Feedback-loop complaints** (#191): ARF reports (RFC 5965) arrive as unauthenticated inbound mail and can suppress a recipient (`complaint`, the strongest reason) or unsubscribe them (`opt-out`). **Forgery is bounded by the Message-ID link:** a report counts only when its `Original-Message-ID` (or the reported message's `Message-ID`) exactly matches the Message-ID of an email BunMail sent, and the suppression is filed under that email's API key for one of its recipients. BunMail's Message-IDs carry 128 random bits, so only someone holding the delivered message (a recipient, their mailbox provider, anyone they forwarded it to) can name one; unlinkable reports are logged and dropped, before any DKIM lookup. The recipient is the report's `Original-Rcpt-To` when it was a recipient of that email, else the email's only recipient; with several recipients and no usable `Original-Rcpt-To` nothing is suppressed (the webhook fires with `recipient: null`). DKIM on the report is verified with mailauth and logged, **not required** (not every provider signs its reports); the check runs only for linked reports and is bounded (no signature: no lookup; more than five signatures or a header section over 64 KB: skipped; 10 s cap). Reports are never stored as inbound mail and never trigger an inbound notification. **Residual:** a party holding a delivered message can suppress its recipient under the sending key, which is equivalent to that recipient unsubscribing; on a multi-recipient email, a recipient who can see a co-recipient's address (to/cc) can name it in `Original-Rcpt-To` and suppress it, the exposure the bounce path had before its signed return paths (#236). Requiring a DKIM pass from a known feedback-loop domain would close both, at the cost of dropping reports from providers that do not sign.
- **Parsers on the inbound path are bounded.** Every parser of untrusted bytes (DSN, ARF feedback report (#191), DMARC heuristic and report, mailparser, the inbound notification builder, the recipient parser) has a unit test that feeds it generated input at the accepted size cap and asserts a time budget (#232). The recipient address regex is linear by construction (domain labels exclude the dot) and addresses over 254 characters are dropped before any regex runs, at `parseRecipients`, at SMTP submission ingestion and on inbound `MAIL FROM`; the previous regex backtracked quadratically on a malformed address and the submission path fed it uncapped header addresses.

### HTTP API hygiene

- **Per-API-key rate limiting** (`src/middleware/rate-limit.ts`): fixed window, 100 requests / 60 s by default (`API_RATE_LIMIT_MAX` / `API_RATE_LIMIT_WINDOW`). Covered by an integration test that sends requests through a real plugin; the e2e suites stub this middleware, which is how a missing `.as("scoped")` once left it inactive on every route.
- **Dashboard login brute-force protection** (#109, `src/middleware/login-rate-limit.ts`): `POST /dashboard/login` counts failed logins of every kind **per client IP** (sliding window, 5 failures / 15 min by default) and returns HTTP 429 with `Retry-After` once the limit is hit, before any database or argon2id work; a successful login gives back only its own attempt, so earlier failures stay until the window ends and an account of one's own cannot be used to reset the count between guesses at another (#256). IPv6 clients are counted per `/64`, IPv4-mapped addresses as their IPv4 (#256). Together with argon2id and the 15-character owner password minimum, this is what stops online guessing. There is deliberately no per-account lockout (anyone could lock the owner out); see §6. The client IP is resolved by counting `DASHBOARD_TRUSTED_PROXY_HOPS` entries from the **right** of `X-Forwarded-For`: the leftmost entry is attacker-controlled and never trusted (default `0` ignores the header and uses the raw socket IP).
- **Cleanup interval** (#22): the in-memory rate-limit maps (per-API-key and per-IP login) are pruned every 5 minutes so distinct keys / IPs can't grow them unbounded.
- **CORS:** none configured by default: the API is intended for server-to-server use. Operators that need browser-side access should add CORS deliberately.

### Public unsubscribe endpoint (#249)

`GET` and `POST /u/:token` are the only unauthenticated routes that change data (`src/pages/unsubscribe.plugin.tsx`), plus the `unsub+<token>@<domain>` mailbox on the inbound receiver. Each suppresses one recipient under one API key.

- **Forgery is bounded by the HMAC.** The token is `<email id>.<MAC>`, the MAC an HMAC-SHA256 (128 bits) over email id and recipient (the email row, which the token must match, fixes the API key), keyed by HKDF from `DKIM_ENCRYPTION_KEY`, compared in constant time against values recomputed from the email row. Without the key, nobody can mint a token for an address, and a valid token unsubscribes only the one recipient it was sent to, under the key that sent it. Mail with cc or bcc gets no token (all recipients see one header).
- **Enumeration and guessing** are rate limited per client IP (30 a minute, IPv6 per /64) and every failure (malformed, unknown or purged email, wrong MAC) gives the same `404` page; the token is never echoed and the address is shown masked.
- **Prefetch and link scanners** cannot unsubscribe anyone: `GET` only renders a confirmation page; only `POST` (RFC 8058 one-click or the confirmation button) suppresses.
- **No CSRF check on the POST**, by design: mailbox providers POST cross-origin from their servers. A forged cross-site POST needs the token and can do nothing the token holder could not.
- **Inbound mailto:** an invalid token or a domain other than the email's sender domain is refused at `RCPT TO` (`550`), so nothing is stored and BunMail sends no bounce to a possibly forged sender; a valid one is never stored as inbound mail.
- **Responses:** `Cache-Control: no-store`, `Referrer-Policy: no-referrer` (keeps the token out of `Referer`), `X-Robots-Tag: noindex`, the page CSP with no script, every interpolation escaped.
- **Key rotation:** rotating `DKIM_ENCRYPTION_KEY` invalidates every link already sent (SECURITY.md, Rotation).

### Webhooks

- Outgoing webhook payloads are HMAC-SHA256 signed using the per-webhook secret. The signature covers `<unix-timestamp>.<raw-body>`; the timestamp is shipped in the `X-BunMail-Timestamp` header and the signature in `X-BunMail-Signature` (#43). Each retry attempt is signed with a fresh timestamp, so a replayed delivery from yesterday fails the freshness check on the receiver. Recommended consumer check: `|now - timestamp| < 5 min`.
- **Tenant-scoped dispatch.** An event is delivered only to webhooks owned by the API key that owns the email (the outbox insert `enqueueEvent` filters on `api_key_id`, #184). Previously every subscribed webhook received every key's events, leaking recipients and subjects across keys; migration `0014` deletes the deliveries that leaked that way. Inbound `email.received` has no owning key and goes only to admin keys' webhooks; restricted keys cannot subscribe to it (`INBOUND_EVENTS_REQUIRE_ADMIN`), keeping inbound mail admin-only (#130).
- **Untrusted responses.** The receiver is tenant-controlled. Bun's `fetch` inflates a compressed body in native code regardless of how much JavaScript reads (a 0.5 MB gzip response cost about 1 GB of memory in testing), so the worker fetches with `decompress: false`, never decodes an encoded body (its preview is a placeholder), streams at most 8 KB of an identity body for the 2 KB preview and cancels the rest. `Accept-Encoding: identity` is requested so honest receivers' previews are kept. Each attempt is counted when it is claimed, so a response that crashes the process still uses up an attempt and the delivery ends at `failed` instead of crash-looping the restarted server.
- **SSRF guard (#128).** Webhook URLs are tenant-supplied and fetched server-side, and the response is read back through the delivery API, so an unvalidated URL is an *exfiltrating* SSRF. `src/utils/ssrf-guard.ts` validates every URL **at creation and again before each delivery attempt** (DNS can rebind): scheme must be `https` (or `http` only if `WEBHOOK_ALLOW_INSECURE_HTTP=true`), and the host is resolved and rejected if any address is private/loopback/link-local/ULA/CGNAT/metadata (incl. `169.254.169.254`; IPv6 site-local, multicast, local-use NAT64 and scoped addresses; and IPv6 forms that embed an IPv4 address, IPv4-mapped, IPv4-compatible, NAT64 `64:ff9b::/96` or 6to4, in dotted or hex-group notation, judged by the IPv4 rules). Teredo addresses are not unpacked: reaching one needs a Teredo interface on the server. **The connection is pinned to the validated address:** each attempt resolves the host exactly once, and the request goes to that address (`buildPinnedRequest`, which fails closed if the URL cannot carry exactly that address) with the original `Host` header, the host name as TLS SNI and the certificate verified against the host name before any byte of the request is sent. Each attempt opens a fresh connection (`keepalive: false`). Delivery uses `redirect: "manual"` so a 3xx into an internal address can't bypass the check. An egress firewall / proxy remains the defense-in-depth control for hostile multi-tenant use.

- **Per-key webhook limits (#258).** A key may have at most `WEBHOOKS_MAX_PER_API_KEY` webhooks (default 10; count and insert under a lock on the key's row, so parallel creates cannot overshoot), which bounds the fan-out of each event. A delivery can be replayed at most 5 times per hour (`429 REPLAY_LIMIT_REACHED`), counted after the ownership check so another key can neither spend the budget nor probe delivery ids. Finished deliveries, `failed` included, are purged after `WEBHOOK_DELIVERY_RETENTION_DAYS`, so a key whose receiver stays down cannot grow the table without bound. The webhook and template lists are paginated (at most 100 rows a page).

### Repudiation: the audit log (#221)

- **Mitigated by #221.** Sign-ins (success, each failure with its reason, the 2FA step), sign-outs, session revocations and token reuse, two-factor changes, password changes and resets, owner setup links, invitations, role changes, deactivations, removals, ownership transfers, and API key, domain, webhook and suppression changes from the dashboard and the REST API are recorded in `audit_events` with the actor (a user, an API key or BunMail itself), the target, the outcome, the client IP and the user agent; admins and the owner read it at `/dashboard/audit-log` (members: 403). Changes that run in a transaction record their event in the same transaction, so a change cannot commit without its record.
- **Append-only through the application.** The code has no update and no delete except the retention purge, and a statement-level trigger refuses every `UPDATE` of the table from any connection, so a bug or an injected query cannot rewrite an entry. No foreign keys: deleting an account or a key keeps its history (labels are snapshots).
- **Bounded and clean.** A login flood from one address records at most `DASHBOARD_LOGIN_RATE_LIMIT_MAX + 1` rows per window (the lockout once); an unknown account's typed address is never stored; metadata is typed per action and a secret-looking key is dropped; a webhook is labelled by its origin only.

### Dashboard XSS

- `@kitajs/html` does **not** auto-escape interpolated children: escaping requires the `safe` attribute on the enclosing element. Every interpolation of stored/user data must carry `safe`; missing it is a stored/reflected XSS.
- **DMARC pages (#131):** aggregate-report fields (`orgName`, `domain`, `sourceIp`, `disposition`, auth domains/results, raw XML) arrive over the unauthenticated inbound path and were rendered without `safe`: an emailed report with `<img onerror>` would execute in the admin origin. Now all such fields (both DMARC pages) carry `safe`, covered by a render-level regression test (`test/unit/dmarc-xss.test.ts`).
- **Templates and suppressions pages:** template `variables` and suppression addresses are writable by any API key, including restricted ones, so they are attacker-controlled from the dashboard's point of view. The variables cell carries `safe`, and the suppression Delete confirmation is static text: no stored value is ever placed inside an inline event handler, where `@kitajs/html` attribute escaping (double quotes only) is not enough. Covered by `test/unit/dashboard-xss.test.ts`.
- **Tooling:** `@kitajs/ts-html-plugin`'s `xss-scan` CLI finds unescaped children. 4.1.4 has two blind spots that `test/xss-gate.ts` (what `bun run lint:xss` runs, #229) closes: it only checked the false branch of a conditional expression (`cond ? a : b`), so the installed copy is patched before every scan to check both branches (the gate fails loudly if the scanner source changes); and it never checks attribute values, so the gate also rejects any dynamic event-handler attribute (`onclick={...}`) under `src/pages`, where `@kitajs/html` escapes only `"`. Since #255 (part 2) it rejects every event-handler attribute, every inline `<script>` (other than a `type="application/json"` data block) and the Tailwind CDN under `src/pages`, and the pages run under `script-src 'self'`, so an XSS that slips past `safe` cannot run injected script either. It runs as a CI gate since #150, which also audited every flagged interpolation. Inbound **email body** HTML is separately rendered in a sandboxed iframe (`html-preview.tsx`, `sandbox` without `allow-scripts`).

### Logging

- The structured logger doesn't emit secrets: `key_hash`, `dkim_private_key`, session tokens and their hashes are never logged (session log lines carry the `ses_` id, which is not a credential). Failed logins are logged at `warn` with the IP, the reason and the email through `redactEmail`; token reuse at `warn` with the user, session and IP.
- **One documented exception: the owner setup link (#215).** `Owner setup link` is logged at `warn`, raised to `error` when `LOG_LEVEL=error` (so no log level hides it), once per minted token, because the logs are the only channel to the operator on first boot. The token is single use and expires after 24 h; its hash is never logged, and the owner address goes through `redactEmail`, so it is masked only when `LOG_REDACT_PII` is on (the production default). `reset-owner` writes the link to the operator's terminal on stdout, outside the logger. Database errors on the users paths (owner, login, sessions) are logged as `UserStoreError` (SQLSTATE only), never with drizzle's query parameters (password hash, token hashes, emails). Successful setups (`Owner setup completed`, with the client IP) and cross-origin setup posts are logged at `warn` for audit. Shipped logs therefore hold a live credential until the link is used or expires: see §6.
- **Safety net (#284):** the logger replaces the value of any field whose name ends in `password`, `secret`, `token`, `tokenHash`, `secretHash`, `privateKey`, `authorization`, `cookie` or `apiKey` (any case, any depth) with `[REDACTED]`, so a secret that slips into a new log call never reaches the output. Request lines log the path without its query string and mask credential-like path segments.
- Recipient PII in log records is redacted (`a***@example.com`) when `LOG_REDACT_PII=true` (#33). Default is `true` in production and `false` in development so dev logs stay debuggable. Webhook payloads still carry full addresses: consumers depend on them; only logs are masked.

### Container

- The image runs as the unprivileged `bun` user (uid 1000), not root (#167). An RCE in the app, `mailparser`, or the DMARC XML path (reachable from **unauthenticated** inbound mail) lands as an unprivileged user that can't modify the application's own files, which are root-owned and read-only to it.
- Binding 25/587 without root uses the `net.ipv4.ip_unprivileged_port_start=0` sysctl, scoped to the container's network namespace, rather than `CAP_NET_BIND_SERVICE` or file capabilities on the `bun` binary.
- An SMTP server that can't bind its port exits the process instead of logging and continuing, so a mail outage can't hide behind a passing HTTP health check.

## 5. What's NOT mitigated in code (operator responsibilities)

These are the controls the codebase cannot apply for you. If you skip them, the threat model breaks.

| Control | What you must do |
|---|---|
| **Disk encryption / DB volume** | DKIM private keys are encrypted at rest (#23) so a DB dump alone leaks no signing material. Dashboard password hashes (argon2id), session token hashes, recipient lists, and inbound mail bodies are **not** encrypted: treat the Postgres volume and any backups as secret-bearing. Encrypt the disk; lock down backup storage; keep `.env` (which holds the DKIM key) on a different rotation/storage tier than the DB dump. |
| **Reverse proxy + TLS termination** | The dashboard ships HTTP-only on port 3000. Put it behind nginx/Caddy/Cloudflare with a real cert. Never expose `:3000` directly. Set `DASHBOARD_TRUSTED_PROXY_HOPS` to the number of trusted hops (`1` for a single proxy) so the login throttle (#109) keys off the real client IP, and because that only holds if the origin is unreachable directly, the "never expose `:3000`" rule is what keeps `X-Forwarded-For` trustworthy. |
| **Firewall / port hygiene** | Inbound SMTP listens on port 25 (or 2525 if `SMTP_PORT=2525`). Block every other port from the public internet. Specifically block `:5432` so the database isn't reachable from anywhere except the app process. |
| **SMTP submission exposure (#120)** | The submission server (port 587, opt-in) authenticates with an API key. With no TLS configured it allows plaintext AUTH (`allowInsecureAuth`), so the key travels in the clear, only run it that way on a trusted network (same host / private Docker network). To expose it more broadly, configure `SMTP_SUBMISSION_TLS_CERT`/`_KEY` (STARTTLS) and firewall port 587 to the specific apps that use it. Rotate any API key used for SMTP submission like any other secret. |
| **`.env` secrecy** | `DATABASE_URL`, `DKIM_ENCRYPTION_KEY` and `POSTGRES_PASSWORD` live in `.env` (the dashboard has no secret there since #216: remove any leftover `DASHBOARD_PASSWORD` and `SESSION_SECRET`). Don't commit it. Don't paste it into chat tools. Rotate if it leaks. |
| **PTR / reverse DNS** | Set the rDNS record for your sending IP to match `MAIL_HOSTNAME`. Without this, mail goes to spam regardless of code-side hardening. |
| **SPF / DKIM / DMARC publishing** | BunMail tells you what records to publish; you have to actually publish them and keep them current. |
| **IP reputation monitoring** | Watch [mxtoolbox.com/blacklists.aspx](https://mxtoolbox.com/blacklists.aspx) for your sending IP. Address listings within hours, not weeks. |
| **OS / runtime patches** | `bun upgrade`, `apt upgrade`, container image rebuilds. The codebase can't keep itself current. |
| **API key rotation** | Treat `bm_live_…` keys like any other secret. Revoke (set `is_active = false`) and rotate periodically. Revocation takes effect everywhere: REST, open SMTP submission sessions (checked per message) and the key's webhooks (no further events; queued deliveries failed). |
| **Backup integrity** | Test restores. A backup you can't restore is not a backup. |
| **Dashboard access scope** | Admins and the owner can invite accounts (#217); roles are enforced per route (#222). Every role, member included, reads every email across every API key: roles limit what an account can change, not what it can see, so invite only people who may see all mail. Revoke pending invitations you no longer need. Don't share the owner password; if it or a session cookie may have leaked, run `reset-owner` (signs every session out) and set a new password. Deactivate or remove accounts that no longer need access at **Users** (#218): it signs them out at once. After an ownership transfer, update `BUNMAIL_OWNER_EMAIL` to the new owner. |
| **Password reset links (#277)** | The issuing admin sees the reset link once and must deliver it over a private channel: anyone holding it within the hour, before it is used, can set the account's password. Prefer a channel the account holder is already authenticated on; issue a new link (which kills the old one) if in doubt. Set `APP_BASE_URL`, or the link points at localhost. |
| **Invitation links (#217)** | Without `SYSTEM_MAIL_FROM` (or with its domain missing or not DKIM-verified) the inviter gets the accept link on screen and must deliver it: share it over a private channel, since anyone holding it until it is used or expires creates the account. Set `APP_BASE_URL`: without a usable one no invitation is emailed and every link is shown to the inviter instead. Keep `INVITE_EXPIRY_DAYS` short. |
| **Scaling caveats** | Rate limit state is in-memory: multiple replicas would each have their own counters. This applies to both the per-API-key limiter and the per-IP dashboard login throttle (#109): across N replicas an attacker effectively gets N× the login attempts before any one replica locks them out. The queue's `queued → sending` transition is atomic via `FOR UPDATE SKIP LOCKED` (#20), and recovery is lease-based (#180): a replica's boot no longer resets rows another replica is sending, so the queue is replica-safe end to end. Dashboard sessions are in Postgres since #216, so they work on every replica; the in-memory rate limits (including the webhook replay budget, #258) and the one-time reveal store (#132) are still per-replica. Use a sticky load-balancer (or consolidate to a single rate-limit Redis) if you scale out. |

## 6. Known residual risks

These are real but accepted (or pending) trade-offs.

- **Owner setup claim window (#215).** Until the setup link is used or expires (24 h), anyone who can read the app logs (`docker compose logs`, a log shipper, a third-party log service) can open it first and set the owner password, which also signs them in. Mitigations: claim right after the first deploy, keep logs on the host during that window, watch for an unexpected `Owner setup completed` line, and recover with `reset-owner`, which signs every owner session out at once and again when its link is completed (#216).
- **Only the latest setup link works with multiple replicas (#215).** Each replica that boots while setup is pending revokes the previous link and logs a new one (serialized by the `bunmail:owner` lock), so earlier links in the logs fail. Operators must use the most recently logged link. Accepted: the issue specifies replace-on-restart.
- **Login throttling is per IP only (#109, #216).** Failed logins are counted per client IP; there is no per-account counter or lockout, because a lockout would let anyone lock an account out. Credential stuffing spread across many IPs is slowed only by argon2id and the 15-character password minimum (which invited accounts share, #217). There is deliberately no global failure budget across addresses either (#256): it would let anyone spraying failures from many IPs lock every account out of the dashboard, and argon2id with a 15-character minimum already makes distributed guessing impractical. Two-factor authentication (#220) is the answer for accounts that matter: with it on, a guessed password alone opens nothing, and the second step **is** throttled per account (an attacker must hold the password to reach that budget, so this per-account lockout costs them the password first).
- **An invitation link is a bearer credential until used or expired (#217).** Whoever holds it creates the account with the invited role; the address on the invitation is not verified (the link may have been shared by hand). Mitigations: single use, `INVITE_EXPIRY_DAYS` (default 7), revocable and replaced on resend or re-invite, dead once its inviter is deleted, disabled or demoted, emailed only from a DKIM-verified sender, and `Invitation accepted` logged at `warn` with the new user, the inviter and the client IP so an unexpected acceptance is visible. The copy-link path relies on the inviter delivering the link privately.
- **A password reset link is a bearer credential for one hour (#277).** Whoever holds it sets the account's password and is signed in as that account; nothing proves the person using it is the account holder, so the delivery channel is the trust boundary, as for a hand-shared invitation link. Mitigations: issued only by an account allowed to manage the target, shown once to the issuer only (never emailed, logged or in a URL), single use, 1 hour on the database clock, one live link per account, dead once the account or the issuer is deactivated or the issuer loses the right to manage the account, and `Password reset completed` logged at `warn` with the account, the issuer and the client IP. A rogue admin could reset a member's password and sign in as it; that is within what an admin can already do to a member (deactivate, remove) and is logged both at issue and at use.
- **Reset links and `reset-owner` remove two-factor authentication (#220).** Completing an admin-issued reset link removes the account's second factor (the lost-phone recovery path), so whoever holds a live reset link signs in without 2FA. Same mitigations as the link itself (issued only by an account that may manage the target, shown once, single use, 1 hour), plus the `warn` line `Password reset completed` with `twoFactorRemoved`, and every session of the account is signed out. For the owner, completing a `reset-owner` link does the same; issuing it removes nothing, so an abandoned reset does not weaken the owner, but anyone with shell access can produce such a link (shell access already owns the database). Under `REQUIRE_2FA` the account must enrol again right away.
- **TOTP secrets are as safe as `DKIM_ENCRYPTION_KEY` (#220).** They are encrypted at rest with it; a database dump plus the key yields every account's TOTP secret (the password hashes would still have to be cracked). Keep the key out of the database host's backups, as for DKIM keys. A key change without re-encryption makes existing authenticator codes fail (recovery codes still work).
- **Two-factor state is per replica where it is in memory (#220).** The code-check budgets and the "already emailed" mark of the exhausted-budget alert live in process memory, so across N replicas an attacker who knows the password gets about N times the code guesses (still small against 10^6 codes with three valid at a time, see slow guessing above) and the account may get up to N emails per window; a restart resets them. Recovery codes shown after enrolment go through the per-replica reveal store. The pending enrolment secret and the replay counter are in Postgres, so they hold across replicas.
- **The second-factor budget can lock an account's 2FA step for a window (#220).** Someone who knows the password can spend the per-account login budget and keep the real user from completing the code step until the window ends (15 minutes). Accepted: it needs the password, the account is emailed when it happens, and the user should change the password; the alternative (no per-account budget) would let distributed guessing of the 6-digit code go unbounded. A stolen **session** cannot do this: in-session checks have their own per-session budget and the session is revoked when it runs out.
- **Slow online guessing of the code (#220).** With the password, an attacker can try 5 codes per 15 minutes per account forever, about 480 a day; with three valid codes at any moment that is roughly a 0.14 % chance per day, so a patient attacker who already holds the password has meaningful odds over months, and one that stays under 5 failures per window never triggers the email. Mitigations: guessing needs the password (change it when the exhausted-budget email arrives, or when anything looks off), every failure is logged at `warn` (`Two-factor sign-in failed: invalid code`), and an operator can watch for repeated failures per `userId`. Accepted for a 6-digit TOTP; passkeys (#223) would remove it.
- **Admin-issued resets remove 2FA by design (#220).** An admin can reset a member's password (and the owner an admin's), and completing the link removes the account's second factor: a malicious or compromised admin can take over a member account despite 2FA. Accepted: admins already manage those accounts and can deactivate them, the recovery path for a lost phone needs it, and the account is emailed (`removed_by_reset`) and every one of its sessions signed out when it happens.
- **New-device alerts have blind spots (#282).** (1) An attacker who steals the `bm_device` cookie together with the password (malware on the victim's machine) signs in as a known device and gets no alert; the cookie is `HttpOnly` and only proves "this browser signed in before", so it buys nothing without the password. (2) The account's very first device, and on an upgraded instance each account's first sign-in after the upgrade, is recorded silently: an attacker who signs in first is the "first device" and the real user's later sign-in triggers the alert instead. (3) Clearing cookies or a private window makes a real user's own browser look new (a false alert, by design). (4) Alerts depend on `SYSTEM_MAIL_FROM`: without it the event is only logged. (5) Only password sign-ins alert; setup, invitation, reset and password change links are protected by their own one-time tokens.
- **The audit log lives in the database it audits (#221).** The trigger stops `UPDATE`s, but the application's database role owns the table, so a database superuser, or anyone with arbitrary SQL as that role (it can drop the trigger), can still alter or delete entries, and the retention purge deletes them by design. Nothing is shipped off the host (no syslog or external sink). Mitigations: back the database up off-host; a separate, insert-only role for the application, or shipping entries to an external store, is not implemented. Events recorded outside a transaction (sign-ins, sign-outs, API key, domain, webhook and suppression changes) are best effort: if the insert fails the action still happens and an `error` line (`Audit event not recorded`) is logged. SMTP submission AUTH failures and REST requests with an invalid key are logged but not recorded.
- **Outbound TLS can be downgraded (#250).** Outbound STARTTLS is opportunistic with no certificate verification, and neither MTA-STS nor DANE is implemented, so a network adversary on the egress path can strip the STARTTLS offer (the mail goes in plaintext) or present any certificate. Since #250 a stripped session is recorded as `tls: "plaintext"` on its delivery-state entry and badged on the email page, so the downgrade is visible after the fact; it is not prevented.
- **Rate-limit state is per replica.** The login throttle (and the ownership transfer throttle built on it, #218) lives in memory, so across N replicas an attacker gets about N times the attempts (see §5, Scaling caveats).
- **~~Inbound notifications relay attacker content under the operator's signature.~~ Mitigated (#250).** A notification is DKIM-signed by the operator's own domain, and it copied the inbound subject into its own subject plus a 200-character preview with links, so a phishing message arrived with a trusted signature, and a flood of inbound mail became a flood of notifications. Now the subject is fixed (`New email for <recipient address>`), the body is plain text with no inbound subject, text or link unless `INBOUND_NOTIFY_PREVIEW=true` (then flattened to one line, every `http://`, `https://` and `www.` link replaced), automatic inbound mail (auto-replies, bulk and list mail, a null return path) is not notified, and each recipient address gets at most 5 notifications per 10 minutes, each recipient domain at most 30. The receiver no longer logs the inbound subject. **Residual:** the sender address (unauthenticated: inbound SPF/DKIM/DMARC is not verified) is still shown, as plain text with links removed, and a mail client may still turn an address or a bare domain name into a link; with the preview on, bare domain names in the subject or preview are not removed either. The notification budgets (5 per address and 30 per domain per 10 minutes) are in memory per replica, so N replicas allow N times the budgets, and a restart resets them; the per-domain budget closes the catch-all bypass, where a sender spread mail over many addresses of a domain that accepts any local part, each with its own budget.
- **~~Noisy neighbour between API keys.~~ Mitigated (#258, with #176 and #250).** One key could fill every queue batch (global FIFO claims), keep SMTP sessions open for minutes, register unlimited webhooks, replay deliveries without limit and grow `failed` deliveries forever. Now: fair round-robin claiming for emails and webhook deliveries, an in-flight cap and bounded SMTP sessions, a per-key webhook cap, a replay budget, paginated webhook and template lists, and retention for failed deliveries. **Residual:** the replay budget lives in memory per replica, like the other limiters, so with N replicas a delivery can be replayed about 5 × N times an hour, and a restart resets it. Fairness is per API key: one key still competes with itself, and a deployment that hands many keys to one tenant gives that tenant several shares.
- **The one-time reveal store is per replica (#132, #280).** Since #280 a reveal is bound to the kind, user and session that created it (mitigated: a leaked token is useless to other accounts). It stays in memory per process: on a multi-replica deploy a create on one replica and the follow-up GET on another miss the token, and the operator revokes and recreates.
- **Session token rotation has two known limits (#216).** (1) A lost response: if the response carrying a rotated cookie never reaches the browser (a dropped connection), its next request after the 30 s grace presents the replaced token and is treated as reuse, signing the user out of every session. Rare, and accepted as the price of detection. (2) An idle victim who never comes back: a thief's requests rotate the token and keep the session alive, up to the 7-day cap, until the real browser presents its old token (detected via `session_token_history`, every session revoked), the user signs the unknown device out from Active sessions (#281) or changes the password (#279), the owner runs `reset-owner`, or the cap ends it. Detection needs the real browser (or its cookie) to be used again.
- **`reset-owner` keeps the old password until its link is completed (#216).** It signs every owner session out immediately, but someone who knows the current password can sign in again until the new link is used. Complete the link promptly when a compromise is suspected.
- **~~Setup, invitation, reset and login pages load the Tailwind CDN script.~~ Mitigated (#255).** These pages loaded `cdn.tailwindcss.com` while a setup, invitation or reset token or a password was in the DOM. Every response carries a baseline CSP (no plugins, no `<base>`, forms to this origin only, no framing), `nosniff`, `X-Frame-Options: DENY` and, behind HTTPS, HSTS, and the dashboard is never cached (part 1). Since part 2 no page loads third-party code: the stylesheet is built at deploy time and served by BunMail with the only script, `/dashboard/assets/dashboard.js`, and the landing page, the dashboard and the HTML 404 page send `script-src 'self'` without `'unsafe-inline'` (`docs/dashboard.md`, Security headers). Residual: `style-src` keeps `'unsafe-inline'` for the email preview's inline styles, and `img-src https:` lets a previewed email load remote images (a tracking pixel fires when an operator opens it, as before).
- **Outbound certificate validation is relaxed** (`rejectUnauthorized: false` in `mailer.service.ts`). MTA-to-MTA delivery routinely hits self-signed and expired certs; refusing them would mean dropping legitimate mail to a substantial fraction of receivers. Per-domain `requireValidCert` is folded into the Bun-native SMTP client roadmap in #60 (subsumes #37, #42).
