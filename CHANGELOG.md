## [Unreleased]

### Upgrade notes

- **A TLS certificate on SMTP submission now means implicit TLS on port 465 (#349).** With `SMTP_SUBMISSION_TLS_CERT` and `SMTP_SUBMISSION_TLS_KEY` set, the submission server speaks TLS from the first byte and listens on `465` unless `SMTP_SUBMISSION_PORT` is set. If your `.env` still sets `SMTP_SUBMISSION_PORT=587` (as `.env.example` used to), implicit TLS runs on 587: remove the line or set `465`, publish the new port (the TLS example in `docker-compose.override.example.yml` now defaults to 465), open it in the firewall, and switch clients to "SSL/TLS" on that port (nodemailer `secure: true`). STARTTLS is not available on Bun: `SMTP_SUBMISSION_TLS_MODE=starttls` refuses to boot. Also refusing to boot now: an `SMTP_SUBMISSION_TLS_MODE` other than `implicit` or `starttls`, a mode without a cert, a cert without a key (or the reverse), and an `SMTP_SUBMISSION_PORT` that is not a whole number from 1 to 65535. With a cert, `SMTP_SUBMISSION_ALLOW_INSECURE` is ignored: AUTH only over TLS. Without a cert nothing changes (plaintext on 587, which still needs `SMTP_SUBMISSION_ALLOW_INSECURE=true`, #133).

- **`verifiedAt` now means "every DNS check passes", and domains are re-checked daily (#250).** Migration `0033` clears `verified_at` on domains where SPF, DKIM or DMARC is not verified (it used to be set by every Verify, whatever the result); the per-check flags and sending are unchanged. After the upgrade a background loop checks every domain within a few minutes, then about once a day, so expect a few TXT lookups per domain per day from the server. A domain whose records keep failing (two definitive failures in a row) loses `verifiedAt` and its failing flags: with `REQUIRE_VERIFIED_DOMAIN=true` and a failing DKIM record, its sends are then refused. Set `DOMAIN_REVERIFY_ENABLED=false` to keep checking on demand only.

- **Signed return paths change how bounces are matched (#236), when `SMTP_ENABLED=true`.** Signed return paths are used for domains whose MX points at this BunMail; other domains keep the From address as envelope sender (the sender domain's MX set must name `MAIL_HOSTNAME`; the answer is cached per domain for an hour, and a DNS error falls back to the From address). No configuration change is needed, but for those domains three things behave differently after the upgrade. Late DSNs for emails sent before it arrive at the plain sender address and are ignored (logged at `warn`, not stored): BunMail no longer links a bounce by its Message-ID. Synchronous `5xx` rejections at send time still suppress, unchanged. Auto-replies and vacation notices sent to the return path (RFC 3834) are dropped, as at every major ESP. Rotating `DKIM_ENCRYPTION_KEY` now also invalidates every return path in mail already sent, with no grace window. The `b+` local part is reserved on domains BunMail receives for: mail to `b+anything@` that is not a valid return path is refused with `550`. With `SMTP_ENABLED=false` nothing changes.

- **Outbound STARTTLS requires TLS 1.2 or later (#250).** Outbound transports now set `tls.minVersion: "TLSv1.2"`. A receiving MX that only offers TLS 1.0 or 1.1 fails the handshake; that failure carries no SMTP reply, so the email is retried on the usual backoff (and fails once `MAIL_RETRY_MAX_AGE_HOURS` passes), never bounced or suppressed. Under Bun 1.3.14 the TLS client already refused versions below 1.2, so in practice nothing changes for such a peer except how fast the attempt ends: a STARTTLS upgrade that reports success but never answers now fails after 60 s instead of holding the MX lock until the 20-minute session cap. STARTTLS stays opportunistic (a peer that does not offer it gets plaintext, now recorded), and certificates are still not verified.

### Added

- **Attachments on the send API and SMTP submission (#181).** `POST /api/v1/emails/send` takes `attachments: [{ filename, content, contentType?, contentId? }]` (Resend-compatible), template sends included; SMTP submission relays the attachments of a submitted message under the same rules. `content` is standard padded base64, decoded strictly (`422 VALIDATION_ERROR` at `/attachments/<i>/content` otherwise). At most 10 files (`422 TOO_MANY_ATTACHMENTS`) and at most `ATTACHMENTS_MAX_TOTAL_MB` decoded in total (new env var, MB of 1,000,000 bytes, default 5, a whole number from 1 to 18, anything else refuses to boot; also the per-file limit; `422 ATTACHMENTS_TOO_LARGE`, SMTP `552`). Filenames are 1 to 255 characters after trimming with no control, line-separator or bidi-control character, no lone surrogate, no `/` or `\` and not only dots; a `contentId` (for inline `cid:` images) is 1 to 128 characters of `A-Z a-z 0-9 . _ % + -`, optionally `@domain`. Executables, scripts and installers are refused with `422 ATTACHMENT_TYPE_NOT_ALLOWED` (SMTP `550`) naming the attachment's index, never its name: by the last extension (46 of them, case-insensitive, so `invoice.pdf.exe` is refused) and by the content sniffed with `file-type` (PE, ELF and Mach-O executables, Java classes and jars, MSI and other Windows Installer files, cabinets, Android, Debian and RPM packages, browser extensions, shortcuts, registry files, CHM, Flash, WebAssembly, disk images), so a PE file named `invoice.pdf` and declared `application/pdf` is refused. The declared `contentType` is never used: the type sent is the sniffed one, a text type for a few extensions, or `application/octet-stream`. Archives and macro-enabled Office files are allowed (documented residuals); for larger files, upload them to your own storage and send a link. Migration `0037` adds `email_attachments` (raw `bytea` bytes plus filename, type, size, Content-ID and SHA-256, FK to `emails` `ON DELETE CASCADE`, unique `(email_id, position)`), written in the email's transaction behind a small storage interface so an object store can be added later, and an `attachments` metadata column to `email_tombstones`. The mailer loads the files for each attempt and sends them on every transaction and retry, inline parts with their `cid` beside the HTML (whose `cid:` references are kept), DKIM signing the whole message. The bytes are dropped (`content = NULL`) in the outcome transaction that marks the email `sent`, `failed` or `bounced`, and by the trash purge; the metadata stays. Email responses carry `attachments: [{ filename, contentType, size, contentId, available }]`, never the bytes; the idempotency snapshot and tombstones keep metadata only. The dashboard's email page lists the attachments with their sizes, and `GET /dashboard/emails/:id/attachments/:position` (the email page's guard) downloads one as `application/octet-stream` with `Content-Disposition: attachment` (RFC 5987 name), `nosniff`, a `sandbox` CSP and `no-store`, or answers `410` once the bytes are gone. No REST download endpoint. Logs carry counts and sizes, never filenames. Docs: `docs/api.md`, `docs/emails.md`, `docs/smtp-submission.md`, `docs/dashboard.md`, `docs/self-hosting.md`, `.env.example`, `ARCHITECTURE.md`, `THREAT_MODEL.md`, `BunMail-Plan.md`, `README.md`.
- **Tags on emails, with filtering (#189).** A send can carry `tags`, a JSON object of string to string, to answer questions like "what is the bounce rate on password resets?". At most 10; keys are 1 to 40 characters of `A-Z a-z 0-9 _ -`, unique ignoring case; values are 1 to 256 characters after trimming (any script), with no control character (CR, LF, NUL and tab included), no line or paragraph separator, no bidi control and no lone surrogate. Anything else is `422 VALIDATION_ERROR` with the path `/tags/<key>` (or `/tags` when the key itself is invalid), never echoing the value. Template sends take them too. Migration `0036` adds the nullable `emails.tags` jsonb column with the GIN index `idx_emails_tags` (`jsonb_path_ops`); the API returns `tags` (`null` when none). `GET /api/v1/emails?tag=key:value` filters on them: split on the first `:`, so values may contain `:` (and `,`); the parameter may repeat, at most 10 times, and every tag must match; it composes with `status`, `source` and pagination, and a bad filter is `422 VALIDATION_ERROR` at `/tag`. SMTP submission adds a tag per `X-BunMail-Tag: key=value` header (split on the first `=`), consumed and never relayed; an invalid tag or more than 10 is refused with `550`. Every `email.*` webhook payload built from an email row (`email.sent`, `email.failed`, `email.bounced`, `email.complained`, `email.unsubscribed`) carries `tags` (`null` when none); `email.received` and `domain.*` do not. The dashboard's email list has a `key:value` tag filter that composes with the status, source and API-key filters and survives pagination, and the email page shows the tags, each linking to the filtered list. Tags are labels, not message content: the idempotency snapshot keeps them, and they are never sent to the recipient. Logs carry tag keys only, never values.
- **`MAIL_MX_RATE_PER_MIN`: a rate budget per provider (#250).** New optional env var (unset: no budget; a whole number from 1 to 100000, anything else refuses to boot): at most that many messages a minute per provider bucket, as a token bucket in memory per replica. A message over it is deferred, not failed: the email goes back to `queued` with `next_attempt_at` at the bucket's next token (plus a small jitter), without counting an attempt, writing an error or firing a webhook, and the email's other recipient domains go ahead in the same attempt. The retry window still counts from creation. Limiting is logged at `info` once a minute per bucket.
- **`MAIL_IP_FAMILY`: choose the outbound address family (#250).** New optional env var, `4` (default) or `6`; anything else refuses to boot. `4` keeps today's behaviour (IPv4 whenever the MX host has an IPv4 address, IPv6 only when it has none); `6` is the mirror. Every address is still checked against the private-address rule.
- **Provider buckets for the outbound throttle (#250).** Every Microsoft MX (`outlook.com` and below, `*.protection.outlook.com`) is one bucket, every Google MX (`*.google.com`, `*.googlemail.com`) another, likewise Yahoo (`*.yahoodns.net`) and Apple (`*.icloud.com`); any other MX host counts as its registrable domain (the DMARC check's heuristic), an address literal as itself. Suffixes match whole labels only, so `evilgoogle.com` or `google.com.evil.net` never join Google's bucket. The bucket is logged at `debug`.
- **Daily DNSBL self-check of the sending IPs (#250).** Nothing told the operator when the server's IP landed on a blocklist, so mail could be rejected or spam-foldered for days unnoticed. About a minute after boot, then every 24 hours (jittered), each sending IP (`MAIL_PUBLIC_IP`, or the A/AAAA records of `MAIL_HOSTNAME`) is looked up on Spamhaus ZEN, Barracuda BRBL and SpamCop: IPv4 as reversed octets, IPv6 as reversed nibbles on ZEN only (the other two do not list IPv6). Only `127.0.0.2` to `127.0.0.11` count as listed, with the Spamhaus codes named (SBL, CSS, XBL, DROP, and PBL shown as a policy listing, not abuse); any `127.255.255.x` answer means the zone refused the query, typically because a public resolver was used, and is reported as `unavailable` with the hint to run a local recursive resolver; NXDOMAIN is not listed; errors, timeouts (5 s) and any other answer are `unknown`, never listed. A new **Blocklists** card next to Server identity on the dashboard home (admins and the owner) shows each address and zone with the time of the last check and, for a listing, the zone's lookup and removal page. Each run logs one `DNSBL self-check completed` line (`job: "dnsbl-self-check"`), plus a `warn` when an address becomes listed and an `info` when it is delisted. Results are kept in memory per replica (no migration). Information only: a listing never holds or refuses mail. New optional env var `SENDING_IP_DNSBL_CHECK` (strict boolean, default `true`) turns it off. See [docs/self-hosting.md](docs/self-hosting.md#blocklists-dnsbl-self-check-250).
- **`SUPPRESSIONS_SHARED_HARD`: shared hard suppressions across API keys (#250).** Suppressions were scoped per key while the sending IP and the DKIM domains are shared, so one key mailing a bad list damaged delivery for every key. New optional env var, `false` by default (only `true` or `false`; anything else refuses to boot). With `true`, every send gate (`POST /api/v1/emails/send`, the dashboard send, SMTP submission and the queue's re-check before a retry, #262) also refuses an address that any key holds an automatic permanent hard bounce or feedback-loop complaint for. Unsubscribes, manual entries (whatever reason they were given) and temporary rows stay per key. The refusal is the usual `422 RECIPIENT_SUPPRESSED` (SMTP `550`) with `suppressionId: null`: it never names the other key or its row, the logs only say `Shared suppression applied` with the requesting key and the redacted address, and each key's suppression list is unchanged. Migration `0034` adds the partial index `suppressions_shared_hard_email_idx` for the cross-key lookup. See [docs/suppressions.md](docs/suppressions.md#shared-hard-suppressions-suppressions_shared_hard-250).
- **A mailbox still full when the retry window ends is soft-suppressed for 24 hours (#250).** Temporary failures that outlasted `MAIL_RETRY_MAX_AGE_HOURS` ended `failed` with no suppression and no bounce event. Now a recipient whose last reply was exactly `4.2.2` (mailbox full) gets a 24-hour soft suppression through `addFromBounce` (a permanent suppression on file is never weakened) and an `email.bounced` with `bounceType: "soft"`, `status: "4.2.2"` and `source: "inline"`, per recipient, in the same transaction as the email's outcome (#184; the degraded save keeps the suppression and logs the lost events). `email.failed` still fires as before. `4.2.0`, `4.7.x`, other 4xx codes and failures with no SMTP reply (DNS, network, TLS, MTA-STS) still get neither. See [docs/bounces.md](docs/bounces.md#inline-5xx-flow-68).
- **From display name, a text alternative for HTML-only mail, an HTML document wrapper, and a send category (#250).** Migration `0035` adds two nullable columns to `emails`, `from_name` and `category`; both are returned by the API (`fromName`, `category`). **`fromName`:** an optional send field, sent as `From: "<name>" <from>` (Nodemailer RFC 2047-encodes non-ASCII names); `from` stays the bare address for the allowed-senders check, the DKIM domain and the return path. 1 to 100 characters after trimming; control characters (CR, LF, NUL included), the bidi controls U+202A to U+202E and U+2066 to U+2069, and `@ < > "` are refused with `422 VALIDATION_ERROR` naming the field, so a name cannot pose as an address. SMTP submission keeps the display name of the submitted `From:` through the same rules, and drops (with a `warn` naming the field) one that fails instead of refusing the mail. **Text alternative:** an email with HTML and no text gets a `text/plain` part derived at send time by a bounded in-repo converter (one linear pass over at most 1 MB of HTML, scripts, styles, `<head>` and comments dropped, links written `text (url)` for http, https and mailto only, output capped at 256 KB), so it goes out as `multipart/alternative`. **Wrapper:** HTML without an `<html>` element is wrapped at send time in a minimal HTML5 document with a UTF-8 charset and a viewport. Neither is stored: the row and the API keep what the caller sent. **`category`:** optional, `transactional` or `marketing`. `transactional` mail is sent without `List-Unsubscribe` and `List-Unsubscribe-Post`. `marketing` mail must be able to carry the per-recipient one-click link (#249): exactly one recipient (no cc or bcc) and an https `APP_BASE_URL` without a query, otherwise the send is refused with `422 MARKETING_REQUIRES_ONE_CLICK` and nothing is queued. Unset keeps today's behaviour. SMTP submission sets it with an `X-BunMail-Category: transactional|marketing` header, which is consumed and never relayed; any other value is refused with `550`. The idempotency snapshot keeps `fromName` and `category`: they label the send, they are not message content.
- **Outbound MTA-STS, RFC 8461 (#250).** Before each attempt the mailer looks up the recipient domain's `_mta-sts` TXT record and, when exactly one valid record announces a policy, fetches `https://mta-sts.<domain>/.well-known/mta-sts.txt`: HTTPS with the certificate verified for that name, no redirects, a 10 s timeout, at most 64 KB, `text/plain` only. The policy host is chosen by the recipient domain, so its addresses go through the same private-address check as MX hosts (`MAIL_ALLOW_PRIVATE_MX` applies) and the request is pinned to the checked address, with the host name as TLS server name. Policies are parsed strictly and cached in memory per domain under their `id` until `max_age` (capped at a year; at most 10,000 domains, the oldest evicted); a failed refetch, a TXT record that disappears or a failed TXT lookup keeps an unexpired cached policy. The cache is per process: each replica fetches on its own, and the first fetch is trusted. **Domains publishing an `enforce` policy now get verified TLS or a retry:** only the MX hosts the policy names are tried, STARTTLS is required, and the certificate must chain to a trusted root and name the MX host. No matching host, a missing STARTTLS or a bad certificate leaves the entry in `retry` (a TLS failure fails over to the next matching host), never a bounce, and the email fails once `MAIL_RETRY_MAX_AGE_HOURS` passes. `testing` policies deliver as before and log at `warn`, once per domain and policy `id`, what enforce mode would have refused (no matching MX host, or a plaintext session); `none` changes nothing. Every `deliveryState` entry gains `mtaSts` (`enforce`, `testing` or `null`), and the email page notes "MTA-STS enforced" next to TLS. DANE, TLS-RPT and inbound MTA-STS are not implemented. Docs: `docs/emails.md`, `docs/api.md`, `ARCHITECTURE.md`, `THREAT_MODEL.md`, `SECURITY.md`, `docs/testing.md`.
- **Scheduled DNS re-verification of domains (#250).** Verify ran only on demand, so a domain whose SPF, DKIM or DMARC record was removed or changed after verification stayed verified. A background worker now wakes every few minutes (jittered), claims the domains that are due (`FOR UPDATE SKIP LOCKED`, safe with several replicas) and runs the same checks as Verify, 8 domains at a time; a passing domain is checked again after `DOMAIN_REVERIFY_INTERVAL_HOURS` (new, default 24, 6 to 168, plus or minus an hour), a failing one after an hour. Each check is `pass`, `fail` (record missing or wrong) or `unknown` (the lookup failed: SERVFAIL, timeout, network), and DNS blips never stop sending: `unknown` changes nothing, one failure only counts, and only the second definitive failure in a row flips a verified domain to failing, in one transaction with a new `domain.verification_failed` webhook event (`{ domainId, domain, failedChecks, checkedAt }`) and a `warn` log line. A failing domain that passes again is verified again and fires the new `domain.verified` event (also fired when a domain is verified for the first time). Both events go to admin keys' webhooks only, like `email.received`, and a restricted key cannot subscribe to them (`403 INBOUND_EVENTS_REQUIRE_ADMIN`). New columns `last_checked_at`, `next_check_at`, `consecutive_failures` and `last_check_result` (migration `0033`); the API returns `lastCheckedAt` and `lastCheckResult` (per check `{ status, reason }`), and the domain page shows when it was last checked, each result and a banner while the domain is failing. `DOMAIN_REVERIFY_ENABLED=false` (new, strict boolean, default `true`) turns the loop off. The loop never sends mail. See [docs/domains.md](docs/domains.md#scheduled-re-verification-250).
- **Implicit MX and failover across MX hosts (#250).** A recipient domain without MX records is now delivered to its own A/AAAA records, as one host of preference 0 (the implicit MX of RFC 5321 5.1), instead of failing; those addresses go through the same private-address check as any MX. MX hosts are tried in preference order, hosts of equal preference in random order, at most 5 hosts and 2 addresses per host per attempt, within the one 20-minute session deadline. Only a connection-level failure (refused, timed out, reset, a STARTTLS stall, no greeting) or a `421` moves on to the next address or host; any other reply from a server that answered decides the attempt, so a `550` from the primary is never retried on a backup. The MX lock is taken per session, for the host actually connected to. Each skipped host or address is logged at `debug`. See [docs/emails.md](docs/emails.md#mx-resolution-and-failover-250).
- **Custom DKIM selector and zero-downtime DKIM key rotation (#250).** `POST /api/v1/domains` and the dashboard's add form accept an optional `dkimSelector`: one lowercase DNS label, 1 to 63 characters (anything else is `422`; the default stays `bunmail`). A domain's key can now be replaced without downtime, admin-only: `POST /api/v1/domains/:id/dkim/rotate` (dashboard: **Rotate DKIM key**) generates a new RSA 2048 key under a dated selector `bm<YYYYMMDD>` (`-2`, `-3`, ... on a same-day collision, never the current selector) and returns its TXT record, also listed in `dnsRecords` with `pending: true`; mail stays signed with the current key. `POST /api/v1/domains/:id/dkim/rotate/complete` switches only once the pending selector's TXT record carries the new key (the comparison Verify uses), otherwise `409 DKIM_PENDING_NOT_PUBLISHED` with the reason; Verify never switches on its own. `DELETE /api/v1/domains/:id/dkim/rotate` cancels. One rotation at a time (`409 DKIM_ROTATION_PENDING`). After the switch the API (`dkimPrevious`) and the domain page show the previous selector with the advice to keep its record for at least 7 days, then remove it; BunMail drops its private key and never signs with it. Domain responses gain `dkimPending` and `dkimPrevious`; no private key, active or pending, is ever returned. Each step is audited (`domain.dkim_rotation_started`, `_completed`, `_cancelled`, metadata `{ selector }`). The boot check of #244 also covers pending keys and reports them apart: an undecryptable pending key only warns, since it holds no mail. Migration 0032 adds the nullable `dkim_pending_selector`, `dkim_pending_private_key` (encrypted like the active one), `dkim_pending_public_key`, `dkim_pending_created_at`, `dkim_previous_selector`, `dkim_previous_public_key` and `dkim_rotated_at` columns to `domains`. See [docs/domains.md](docs/domains.md#key-rotation-250) and SECURITY.md (DKIM key rotation).
- **The DNS records to publish and the MX status, per domain (#250).** The domains API returns `dnsRecords` (each `{ type, host, value, purpose, optional, note? }`) and the domain page shows them as a table with selectable values: the SPF record (`v=spf1 a:<MAIL_HOSTNAME> -all`, with the note to merge it into an existing record), the DKIM record at `<selector>._domainkey.<domain>` pre-split into quoted strings of at most 255 characters, a starting DMARC record `v=DMARC1; p=none; rua=mailto:dmarc@<domain>`, the A (or AAAA) record of `MAIL_HOSTNAME` with the PTR to set at the hosting provider (the address comes from `MAIL_PUBLIC_IP`, or is described when it is unset), and an optional `MX 10 <MAIL_HOSTNAME>` needed only to receive bounces, DMARC reports and inbound mail. The API also returns `mx: { status, hosts }` (`here`, `elsewhere`, `none` or `error`), from the cache the signed return path already uses (#236), and the page shows, with `SMTP_ENABLED`, whether signed return paths, async bounces, DMARC reports and inbound mail are active for the domain and why not. The MX status never gates anything: a domain whose MX serves mailboxes elsewhere keeps working. A domain's DMARC and MX lookups run in parallel under one 5 s deadline (the DMARC fallback shares it), after which a status is `error`; answers are cached (an hour, five minutes after an error) and never fail the request. Listing domains looks up at most 8 at once, so a cold cache on a large install does not fire hundreds of lookups from one request. Create, update and delete never wait on DNS: they return `dmarc` and `mx` as `null` until the next `GET` or **Verify**.
- **Per-MX delivery state, with a TLS record, in the API and on the email page (#250).** Every email in an API response (`GET /api/v1/emails/:id`, the lists, send, trash and restore) has a new `deliveryState` array: one entry per recipient domain, or per recipient when signed return paths (#236) or a partial `RCPT TO` rejection split the group, with `mx` (`null` when the recipient domain has no resolvable MX), `recipients`, `status` (`sent`, `retry`, `failed`), `attempts`, `failureKind`, `failureCode`, `lastError`, `tls` and `updatedAt`. It is empty before the first attempt and visible to the key that can see the email; internal keys are not exposed. Each entry now records whether its latest SMTP session used STARTTLS (`tls`: `starttls`, `plaintext`, or `null` when no session got ready), detected from Nodemailer's own connection events, and when its latest outcome happened. The email detail page shows the same data as a **Delivery by MX** table, every value escaped, with a **Sent without TLS** badge on a delivered plaintext entry (**No TLS** on one that failed or is retrying). Entries written before this release show `tls: null` and `updatedAt` from their delivery time, if any. Docs: `docs/api.md`, `docs/emails.md`, `docs/dashboard.md`, `ARCHITECTURE.md`, `THREAT_MODEL.md`, `SECURITY.md`, `docs/testing.md` (one unit test now needs `node` on `PATH` for a real STARTTLS server).
- **Bounce rate on the dashboard home (#250).** The home page gains **Bounced** and **Bounce Rate** cards: `bounced / (sent + bounced)`, 0 when there is neither. Above 2% the card turns red with a one-line hint to clean the lists. The dashboard stats gain `bouncedCount`, `bouncedLast24h` and `bounceRate`. Docs: `docs/dashboard.md`.
- **`INBOUND_NOTIFY_PREVIEW`: opt back in to a preview in inbound notifications (#250).** New optional env var, `false` by default (only `true` or `false`; anything else refuses to boot). With `true`, a notification's body adds the inbound message's original subject and a preview of up to 200 characters, plain text only, CR/LF removed, with every `http://`, `https://` and `www.` link replaced by `[link removed]`. The notification's subject line never carries the original subject. Docs: `docs/inbound.md`, `docs/self-hosting.md`, `.env.example`.
- **Signed per-recipient return path (VERP) authenticates bounces (#236).** DSNs arrive over unauthenticated SMTP and were linked to an email by the Message-ID in their body, which every recipient of that email can see, so one recipient could forge a bounce for a co-recipient and get that address suppressed under the sender's key. With inbound SMTP enabled (`SMTP_ENABLED=true`, the only setup where DSNs reach BunMail) and the sender domain's MX pointing at this server (`MAIL_HOSTNAME` in its MX set, checked with a per-domain in-memory cache: an hour for an answer, five minutes after a DNS error, which falls back to the plain envelope), each recipient is now sent in its own SMTP transaction whose envelope sender is a signed return path, `b+<email id hex>.<recipient index>.<MAC>@<sender domain>`: the MAC is HMAC-SHA256 (96 bits, lowercase hex, so MTAs that fold case do not break it) over the email id, the recipient's index (to, then cc, then bcc) and the recipient, under a key derived by HKDF from `DKIM_ENCRYPTION_KEY` (no new env var, nothing stored). The inbound receiver accepts a `b+` address only when it verifies against its email row (MAC, index, sender domain), and refuses it with `550` otherwise; a DSN to a verified address bounces exactly that email's recipient, whatever the DSN body names, with the same hard / soft classification, status update and `email.bounced` webhook as before. A DSN to any other address has no effect, and anything else sent to a return path (an auto-reply, an ARF report) is acknowledged and dropped, never stored or notified. Recipients never see each other's return path. The transactions to one MX share one connection (a single-connection nodemailer pool); DKIM, custom headers, `List-Unsubscribe` and `Feedback-ID` are the same in each, and delivery outcomes, failure classification and retries are now per recipient (`delivery_state` entries keyed `<mx host>#<recipient index>`). Single-recipient email is one transaction as before; with `SMTP_ENABLED=false`, or for a domain whose mail is hosted elsewhere (so its DSNs still reach that mailbox and sender-verification callouts still pass), the envelope sender stays the From address and nothing changes. Same domain as the From address, so SPF and DMARC alignment are unchanged. The RFC 3464 parser no longer needs an `Original-Message-ID` (Postfix does not send one). - **Idempotency keys on the send API (#188).** A client that retries `POST /api/v1/emails/send` after a timeout, a 5xx or a serverless retry no longer sends the email twice if it sets the optional `Idempotency-Key` header (1 to 255 printable ASCII characters, no spaces; anything else is `422 VALIDATION_ERROR` naming `/idempotency-key`). The first request with a key is answered as before and its response is stored; a retry with the same key and the same body (compared as canonical JSON, so member order does not matter) creates and queues nothing and returns the first response (same email id, status and warnings) with the response header `Idempotent-Replayed: true`, even after the email itself was purged. The same key with a different body is refused with `422` and `code: "IDEMPOTENCY_KEY_REUSED"`. Keys are scoped to the API key and remembered for the new optional env var `IDEMPOTENCY_KEY_TTL_HOURS` (default `24`, a whole number from 1 to 168; anything else refuses to boot), after which they are reusable; the purge worker deletes expired keys in batches. Concurrent duplicates create exactly one email and never a 500: the key is claimed with `INSERT ... ON CONFLICT` in the transaction that inserts the email, so the others wait for it and replay. A refused send (validation, suppression, unauthorized sender, any error) stores nothing, so it can be retried with the same key. REST only: SMTP submission has no idempotency keys. A replay still counts toward the per-key rate limit. Storage is a new table `idempotency_keys` (migration `0030`) rather than the column on `emails` the issue proposed: a unique index on `emails` cannot express the TTL, and keys should not follow emails through trash and purge. Each key keeps a snapshot of its first response until it expires, without message content (no subject, body or custom headers), so storage overhead is small: a replay fills those from the email while it exists and is not in trash, and returns the original ids and status with those fields `null` once the email is trashed or purged, so deleting an email removes its content everywhere. The inbound SMTP receiver (`SMTP_ENABLED=true`) now recognises ARF feedback reports (RFC 5965, `multipart/report; report-type=feedback-report`) from mailbox-provider feedback loops such as Yahoo/AOL CFL and Microsoft JMRP, before the bounce parser, and never stores them as inbound mail or sends an inbound notification for them. A report counts only when its `Original-Message-ID` (or the reported message's `Message-ID`) exactly matches the Message-ID of an email BunMail sent; unlinkable reports are logged and dropped. `abuse`, `fraud` or no `Feedback-Type`: a permanent `complaint` suppression under the email's API key for the recipient (the report's `Original-Rcpt-To` when it was a recipient of that email, else the email's only recipient) and `email.complained` to that key's webhooks with `{ emailId, recipient, feedbackType, reporter, arrivalDate, receivedAt }`. A complaint takes precedence over every other reason: it upgrades a temporary suppression to permanent and replaces a permanent `bounce`, `unsubscribe` or `manual` one; an address already suppressed as `complaint` changes and fires nothing. Creating one more webhook is refused over REST with `422` and `code: "WEBHOOK_LIMIT_REACHED"`, and on the dashboard with an error flash; the count and the insert run in one transaction holding a lock on the key's row, so parallel creates cannot overshoot. - **One-click unsubscribe becomes a suppression (#249).** Unsubscribe requests used to go nowhere: the RFC 8058 POST body is only `List-Unsubscribe=One-Click`, so the static per-domain URL could not tell who asked, and the default `unsubscribe@<domain>` mailto was never read. Now every email with exactly one recipient (no cc, no bcc) carries a per-recipient `List-Unsubscribe` when `APP_BASE_URL` is an `https://` URL: `<APP_BASE_URL/u/<token>>` with `List-Unsubscribe-Post: List-Unsubscribe=One-Click`, plus `<mailto:unsub+<token>@<sender domain>>` when the inbound receiver runs (`SMTP_ENABLED`; otherwise the domain's `unsubscribeEmail` if set, else no mailto). The token is stateless: the email id plus a 128-bit HMAC-SHA256 over email id and recipient, keyed by HKDF from `DKIM_ENCRYPTION_KEY` (rotating that key invalidates links already sent), lowercase hex so a case-folded mailto still verifies, and `unsub+<token>` fits the 64-character local part. Mail to a valid `unsub+<token>` address is suppressed and never stored as inbound mail; an invalid one is refused at `RCPT TO` with `550`. Repeated requests succeed; an existing permanent suppression is left as it is, a temporary soft-bounce entry becomes the permanent unsubscribe. New webhook event **`email.unsubscribed`** (`{ emailId, recipient, source: "one_click" | "link" | "mailto", unsubscribedAt }`), fired once per suppression to the sending key's webhooks and selectable on the dashboard Webhooks page. Turning it on signs out every other session of the account. Sign-in then takes two steps: the password opens a short `pending` session (10 minutes) that no protected page admits, and `POST /dashboard/login/two-factor` takes the 6-digit code or a recovery code and turns it into a full session with a fresh token. Codes follow RFC 6238 (SHA-1, 6 digits, 30 s, one step of tolerance either side), implemented on Node's `crypto` and tested against the RFC vectors; **a code is accepted once** (the last accepted time step is stored with a compare-and-swap, so even two simultaneous submissions of one code cannot both pass); every code check is budgeted with fixed numbers (5 failures per 15 minutes, always on, whatever `DASHBOARD_LOGIN_RATE_LIMIT_*` says), counted before the check: the login step per account and per client IP (once spent, the pending session is revoked), checks inside a session (turning it off, new recovery codes) per session and per IP, never spending the account's login budget (once spent, that session is revoked). Turning it on needs the current password (a stolen session alone cannot lock the account behind a code only the thief has); turning it off needs the password and a code (an account without 2FA is told so before any password check); new recovery codes need a code from the app. A `password`-level session stops working the moment its account has 2FA, so a login racing the confirmation keeps nothing. **Security emails** (from `SYSTEM_MAIL_FROM`, DKIM-signed, no links, never blocking): 2FA turned on or off, recovery codes replaced, 2FA removed by a reset or `reset-owner` link, and the login code budget exhausted after a correct password (once per window). ### Changed

- **The HTTP body limit and the SMTP submission size limit follow the attachment budget (#181).** The REST body limit was a fixed 12 MB; it is now 12 MiB plus the base64 of `ATTACHMENTS_MAX_TOTAL_MB` plus 64 KiB (about 19.3 MB with the default 5 MB, 36.6 MB at 18), still enforced by Bun with `413` before the body is read. The SMTP submission cap (and its advertised `SIZE`) goes from 10 MiB to 10 MiB plus the MIME encoding of the budget (about 17.4 MB with the default, 35.2 MB at 18). A reverse proxy in front of BunMail may need its own body limit raised to match.
- **Attachments are no longer refused (#181).** The #250 refusal of a REST body with an `attachments` property (`422 ATTACHMENTS_NOT_SUPPORTED`) and of an SMTP-submitted message with attachments (`550 Attachments are not supported`) is gone, replaced by attachment support (see Added). The `ATTACHMENTS_NOT_SUPPORTED` code no longer exists; an empty `attachments` array now sends without attachments.

- **README: relay mode dropped from the roadmap (#182).** BunMail delivers directly to the recipient's servers and will not hand mail to a third-party provider: anyone who wants SES, Resend or Postmark as the sender can use them directly. The deliverability section now lists what does help (warm-up, reverse DNS, the dashboard's Server identity, Blocklists and DNS checks), and the roadmap no longer mentions per-domain TLS observability (#37, #42, now low priority).

- **The outbound throttle is keyed by provider bucket, not by MX host name (#250).** `MAIL_MX_CONCURRENCY` now limits parallel sessions per provider bucket: two host names of one provider (two Microsoft 365 tenants' MX hosts, Google's `aspmx` and `alt1.aspmx`) used to get one session each at once and drew `421 Too many concurrent SMTP connections`; they now share the limit. Not done, on purpose: SMTP connection reuse across sessions (it would weaken the guarantee that a stuck socket is always destroyed, and would have to keep MTA-STS-enforced sessions apart from opportunistic ones), and a `MAIL_SOURCE_IP` setting (Bun 1.3.14 ignores `localAddress` on outbound sockets; pick the source with the host's routing or an SNAT rule instead). See `docs/emails.md`.
- **BunMail's own mail no longer carries `List-Unsubscribe` (#250).** Invitations, sign-in alerts and inbound notifications are sent as `transactional`: nobody subscribed to them, and a default `unsubscribe@<domain>` mailto on them pointed at a mailbox that usually does not exist.
- **A template without a text body keeps the inline `text` of the send (#250).** It used to be dropped, leaving an HTML-only message.
- **`verifiedAt` is set only when every check passes, and Verify follows the re-verification rules (#250).** It was set by every Verify, whatever the result, so a domain with a missing DKIM record showed a "Last Verified" date. It is now set only when SPF, DKIM and DMARC all pass, kept while they keep passing (or a lookup fails), and cleared only when the domain flips to failing. Verify, the inline check of `REQUIRE_VERIFIED_DOMAIN` and the loop share one state machine: a failed lookup no longer marks a record unverified (it is reported as `unknown`), a flag that was verified stays so until the second failure in a row, and every check records `lastCheckedAt` and `lastCheckResult`. SPF with no known sending IP or an SPF `temperror` is `unknown`, no longer a failure. The verify response's `verification` gains `dkimReason` and `checks`. The dashboard shows "Verified Since" instead of "Last Verified".
- **Delivery state is kept per recipient domain (#250).** `emails.delivery_state` entries are keyed by recipient domain (`<domain>#<recipient index>` once split per recipient) instead of by MX host, since each attempt resolves the domain again and may end on a different host; the entry's `mxHost` records the host of its latest outcome. Two domains that share an MX are no longer one transaction, but still share a session when they resolve to the same hosts. In the API, `deliveryState[].mx` is that host, `null` while no host was reached. Rows from before keep working: a pending entry keyed by an MX is routed by its recipients' domains.

- **DMARC verification checks the record, not only that one exists (#250).** **Verify** marked DMARC as verified when any TXT record at `_dmarc.<domain>` started with `v=DMARC1`. It now needs exactly one record matching `v=DMARC1` (any case, whitespace around `=` allowed, its TXT chunks joined first) with a valid `p=` (`none`, `quarantine` or `reject`); two records fail with their own reason (receivers then apply no policy, RFC 7489 6.6.3). A domain without a record inherits the record of its organizational domain, found with a simple heuristic (the last two labels, or three under a common second-level label such as `co.uk`), with `sp=` when set. `p=none` passes with a warning that it does not protect. The tags `p`, `sp`, `pct`, `adkim`, `aspf` and `rua` are parsed strictly (unknown tags ignored, invalid values reported) and returned as `dmarc` by the domains API and on the domain page, with the effective policy; `POST /api/v1/domains/:id/verify` adds `dmarcReason` to `verification`. A domain verified before may turn unverified at its next **Verify** if its record has no valid `p=` or is published twice. The page and the docs now suggest starting at `p=none` with reports to `dmarc@<domain>` instead of `p=quarantine` to `postmaster@`.
- **The dashboard success rate counts bounced emails (#250).** **Success Rate** was `sent / (sent + failed)`, so a bounced email counted neither for nor against it. It is now `sent / (sent + failed + bounced)`, still `n/a` when no email has reached a terminal state; the field keeps its name (`successRate`), so the number drops for a sender with bounces.
- **The inbound receiver no longer logs the subject of received mail (#250).** The `info` line `Inbound email received and stored` carried the raw inbound subject, which is message content and can hold personal data or a phishing text. It now carries the inbound id, the redacted addresses and the size (`bytes`); the subject's length alone is logged at `debug` (`Inbound email subject`). No other log line under the inbound module carried a subject or body text. Docs: `docs/inbound.md`.
- **Inbound notifications no longer relay the message's content, skip automatic mail and are throttled per address (#250).** A notification is DKIM-signed by the operator's own domain, and it copied the inbound subject into its own subject plus a 200-character preview with any links, so a phishing message arrived with the operator's trusted signature on it, and a flood of inbound mail became a flood of notifications. The subject is now always `New email for <recipient address>`, and by default the body only says who it is from (as plain text), when it arrived, its size and, with `APP_BASE_URL` set, the dashboard link; the HTML part is gone (plain text only). `INBOUND_NOTIFY_PREVIEW=true` adds the subject and a link-stripped preview to the body (see Added). Inbound mail that is itself automatic gets no notification: `Auto-Submitted` other than `no`, `Precedence: bulk`, `junk` or `list`, an `X-Autoreply` or `X-Autorespond` header, or a null return path (`MAIL FROM:<>`); logged at `debug`. Each recipient address gets at most 5 notifications per 10 minutes, and each recipient domain at most 30, so a domain that accepts any local part cannot be flooded through many addresses; a notification needs both budgets. Later mail is stored as usual but not notified, logged once per window at `info` (`Inbound notifications throttled for this address` or `... for this domain`), and the next notification for that address says "And N more emails since <time>". The budgets are kept in memory, so they are per replica and reset on restart, and a count no later mail reports is dropped after a day. Notifications keep `Auto-Submitted: auto-generated` and `X-Auto-Response-Suppress: All`. Docs: `docs/inbound.md`, `docs/domains.md`, `docs/self-hosting.md`, `.env.example`, `ARCHITECTURE.md`, `THREAT_MODEL.md`, `README.md`.
- **Fair claiming in the send queue and the webhook delivery worker (#258).** Both claimed a global FIFO batch, so one API key with a large backlog (or a webhook that is down and collecting retries) filled every batch and another key's single email or event waited behind all of it. Each batch is now shared across API keys round-robin: every key's oldest due row ranks first, then its next one, and the batch takes the lowest ranks first, oldest first within a rank. A single key keeps plain FIFO order by due time. Rows are still locked `FOR UPDATE SKIP LOCKED` with the same lease, and concurrent workers' claims stay disjoint. The claim walks each key (each webhook, for deliveries) through new partial indexes `idx_emails_due_per_key` (`api_key_id, next_attempt_at, created_at`) and `webhook_deliveries_due_per_webhook_idx` (`webhook_id, next_attempt_at`), which replace `idx_emails_due` and `webhook_deliveries_due_pending_idx`, so its cost stays one short index probe per key however large the backlog (0.4 ms with 50,000 due rows from one key). Migration `0029_fair_claim_indexes`. Docs: `docs/emails.md`, `docs/webhooks.md`, `ARCHITECTURE.md`.
- **Failed webhook deliveries are no longer kept forever (#258).** The hourly cleanup deleted only `delivered` rows older than `WEBHOOK_DELIVERY_RETENTION_DAYS`; `failed` rows piled up without bound. Both `delivered` and `failed` rows are now deleted once their last change (delivery, final failure) is older than the retention, in batches of 5,000; `pending` rows, including the ones in flight, never are. A replayed delivery's clock restarts when it finishes. `WEBHOOK_DELIVERY_RETENTION_DAYS` (default `30`) is now validated at boot: a whole number from 1 to 365, anything else refuses to start (a typo used to turn into `NaN`, which purged nothing). **Behaviour change:** operators who relied on `failed` rows for forensics past the retention should raise it. Docs: `docs/webhooks.md`, `docs/self-hosting.md`, `.env.example`.
- **Webhook event matching runs in SQL, and webhooks and templates are indexed by API key (#173).** Every email event loaded the key's (or every admin key's) webhooks and filtered their subscribed events in JavaScript, a workaround for the jsonb encoding fixed in #261; the match is now `events @> jsonb_build_array(event)` in the query. Migration `0023` (applied on boot) adds `webhooks_api_key_id_idx` and `templates_api_key_id_idx`. The admin-only list queries named in #173 (API keys, domains, templates, webhooks) stay unpaginated on purpose: they list an instance's own configuration, which stays small. Docs: `ARCHITECTURE.md`, `docs/webhooks.md`, `docs/templates.md`.
- **The dashboard plugin is split per area (#291).** `src/pages/pages.plugin.tsx` held every dashboard route in one file of about 3,600 lines, so nearly every PR touched it. Each area now has its own functional plugin under `src/pages/plugins/` (auth, home, emails, API keys, invitations, users, domains, templates, webhooks, inbound, DMARC, suppressions) and the shared helpers and the session guard live under `src/pages/lib/`. `pagesPlugin` still mounts the public routes, then the session guard, then the protected areas, on the same instance, so the route table is identical: same routes, order, guards, hooks and validation, checked by diffing a dump of `pagesPlugin.routes` before and after. Pure refactor, no behaviour change. Docs: `CLAUDE.md`, `ARCHITECTURE.md`, `docs/dashboard.md`, `docs/users.md`.
- **A flaky CI test gets room to run.** The ownership-transfer burst test runs several argon2id verifies in parallel and hit Bun's 5 s default timeout on busy CI runners (passing on re-run); it now has a 30 s timeout like the other argon2-heavy tests. Tests only.
- **API key middleware tests (#183).** A new integration suite runs the real Bearer-key middleware against Postgres and checks that each malformed `Authorization` header (missing, another scheme, a bare token, an unknown key) gets its own `401`, and that `last_used_at` is written on first use and then at most once a minute per key. With the authorization matrix (#228, every route: no key, invalid and revoked keys, the admin gate, tenant isolation), the deactivated-creator checks (#219) and the allowed-senders suite (REST and SMTP), the middleware no longer depends on stubbed e2e tests for coverage. Tests only.

### Fixed

- **SMTP submission over TLS works: implicit TLS on port 465 (#349).** With a cert configured, the submission server advertised STARTTLS but the handshake never completed (clients saw a timeout or an unexpected EOF), and since plaintext AUTH is refused (#133), no client could authenticate at all. Bun cannot upgrade an accepted socket to TLS on the server side, which is what STARTTLS needs (and smtp-server's own implicit TLS does the same upgrade, so it failed too). The server now terminates TLS from the first byte with Bun's own TLS server and hands each decrypted connection to smtp-server, so every session is TLS: no STARTTLS is offered, AUTH works, and the per-IP limits see the real client address. New env var `SMTP_SUBMISSION_TLS_MODE` (`implicit`, the default with a cert, or `starttls`, which only works on Node and refuses to boot on Bun). The start line logs `tls: "implicit" | "starttls" | "none"`, and `SMTP submission client authenticated` carries `secure`. `smtp-server` is pinned to the exact version 3.19.23, since the handover relies on its `connect` method, and an integration test fails if an upgrade breaks it. The same Bun limitation blocks STARTTLS on inbound port 25 (#345), and implicit TLS is not an option there.

- **REST sends with attachments are refused instead of sent without them (#250).** The send body ignores unknown fields, so `POST /api/v1/emails/send` with an `attachments` field was accepted and the attachments were silently dropped. A body with an `attachments` property, whatever its value (an empty array included, template sends and `Idempotency-Key` sends too), is now refused with `422 ATTACHMENTS_NOT_SUPPORTED` and nothing is queued, as SMTP submission already refuses a message with attachments (`550`). Every other unknown field is still ignored, so no other client is affected. Docs: `docs/api.md`, `docs/emails.md`, `ARCHITECTURE.md`. Superseded in this release by attachment support (#181, see Added and Changed).
- **A DSN reporting a sender policy block no longer suppresses the recipient (#250).** Async DSNs arriving at a signed return path (#236) were classified by the first digit of their status only, so a `5.7.x` (blocked, SPF/DMARC failure, reputation) suppressed a recipient who did nothing wrong, while the same refusal at send time already did not (#246). DSNs now go through the inline classifier (`parseSmtpError`): a `5.7.x`, or a `5.x.x` whose diagnostic names a blocklist, reputation or SPF/DKIM/DMARC, is a policy block unless it also says the recipient does not exist. It writes no suppression and fires no `email.bounced`; a `sent` email is marked `failed` with the reason and `email.failed` fires with `blocked: true` and the inline fields, in one transaction (#184), once per email. `5.1.1` and other `5.x.x` DSNs still hard-bounce, `4.x.x` still soft-bounce. Docs: `docs/bounces.md`, `docs/suppressions.md`, `docs/webhooks.md`, `ARCHITECTURE.md`.
- **A temporary DNS error no longer fails the mail (#250).** Any MX lookup error, `ESERVFAIL`, `ETIMEOUT` or `EAI_AGAIN` included, failed the recipient group at once, with no retry. Only an answer that the domain cannot receive mail is terminal now: it does not exist (NXDOMAIN), it publishes a null MX (`MX 0 .`, RFC 7505), or it has neither MX nor address records, each with a clear `lastError`. Any other resolver error leaves the group in `retry` on the normal backoff, and the domain is resolved again on the next attempt. A null MX, which used to be retried for the whole 48-hour window, now fails at once.
- **Recipients refused at `RCPT TO` are no longer counted as sent (#250).** When one transaction carried several recipients (signed return paths off) and the MX accepted some and refused others, every recipient was marked `sent`. Now the accepted ones are `sent`, and each refused one gets its own delivery-state entry with its own code: a 4xx is retried alone on the next attempt, and a 5xx fails with the same inline hard-bounce handling as a whole-group 5xx (suppression without weakening a permanent one, #191, and `email.bounced` through the outbox, #184).

- **A timed-out SMTP send now closes its connection (#250).** When a session ran past the 20-minute deadline, or a STARTTLS upgrade stalled, the attempt was given up but the connection stayed open: closing Nodemailer's per-send transport does not end a connection that is still busy, and neither does closing a pool. A receiver that accepts and never answers (or stops mid-session, with or without TLS) could pile up open connections in the background. Every MX session is now one pooled connection (also for a single recipient, so there is one code path) whose socket BunMail opens itself through Nodemailer's `getSocket` hook, and when the session ends, however it ends, the socket is destroyed and the pool closed. Retries, the TLS record, the per-recipient split, the deadline and the MX lock are unchanged. Docs: `docs/emails.md`.
- **Webhook events can no longer be lost between a state change and its webhook (#184).** An event was a dual write: the state change committed first (an email marked `sent`, a suppression, a stored inbound message) and the `webhook_deliveries` rows were written afterwards, fire-and-forget, with errors only logged. A crash or a failed insert in between lost the event for good, and nothing detected it. Delivery rows are now written in the same transaction as the state change (a transactional outbox), by one `INSERT ... SELECT` over the matching webhooks (fan-out at write: the match is an indexed lookup on the owning key over at most `WEBHOOKS_MAX_PER_API_KEY` webhooks; the delivery worker, replay and the dashboard are unchanged). Every caller is covered: the queue's outcome with `email.sent`, `email.failed` and inline `email.bounced` (the SMTP send stays outside the transaction), DSN bounces, unsubscribes, feedback-loop complaints and inbound `email.received`. An enqueue failure now rolls the state change back and is logged at `error`, with one exception: a webhook problem never sends a delivered email twice. After a send, the queue retries its outcome transaction twice, then saves the status (and any inline bounce suppression) without the events and logs `Webhook events not recorded for a sent email`; only when the database cannot take even that is the email left to its lease and sent again (at-least-once, as before). The pre-send paths and the SMTP receiver stay all or nothing (the receiver answers `451` so the sender retries). The queue no longer marks a delivered email `failed` when recording its outcome fails, and no longer enqueues `email.sent` or `email.failed` for an outcome it could not save because another claim took the row over. New delivery ids are `wdl_` plus 32 hex characters. See `docs/webhooks.md` (Transactional outbox).
- **A bounce never weakens a permanent suppression (#191).** `addFromBounce` overwrote whatever suppression was on file, so a late DSN (or an inline hard 5xx) for an email sent before a recipient complained, unsubscribed or was suppressed by hand turned that row into a bounce, and a soft bounce into a 24-hour entry that lapsed, after which mail resumed. With complaints now processed this mattered. On conflict a bounce now only rewrites a temporary row (a soft bounce refreshes the window, a hard bounce makes it a permanent bounce); a permanent row of any reason is left exactly as it is, in the same `INSERT ... ON CONFLICT DO UPDATE ... WHERE` statement so it is race-safe. The email is still marked `bounced` and `email.bounced` still fires, its `suppressionId` naming the suppression in effect. A manual `POST /api/v1/suppressions` likewise no longer replaces a permanent `complaint` (it returns that row; delete it first to replace it). Precedence: complaint > unsubscribe / manual / hard bounce > temporary entries. Docs: `docs/suppressions.md`, `docs/bounces.md`, `docs/webhooks.md`, `docs/api.md`, `docs/feedback-loops.md`, `ARCHITECTURE.md`, `THREAT_MODEL.md`.
- **ARF feedback reports no longer fall into the bounce fallback parser (#191).** The bounce parser accepted any `multipart/report`, so a feedback-loop complaint report went to its regex fallback, which linked it by the report's own Message-ID and usually dropped it, acknowledged and stored nowhere. `parseBounce` now returns `null` for `report-type=feedback-report`, and the receiver routes such reports to the new feedback-loop handler first. Docs: `docs/bounces.md`.
- **Outbound SMTP sessions are bounded (#250).** Connecting to an MX and its greeting now time out after 60 s instead of 2 minutes, and a whole session is capped at 20 minutes (the connection is closed and the attempt retried), so a dead or tarpitting receiver can no longer hold its MX lock (and the other mail queued for it) for hours. The 10-minute wait for the reply to the end of DATA is unchanged, as RFC 5321 requires. Docs: `docs/emails.md`.
- **Mail-path fixes from the deliverability audit (#250).** A failed delivery is classified from the SMTP server's reply only (Nodemailer's `responseCode`/`response`, or a line that starts with a reply code), so a connection, DNS or TLS error whose message carries an IP address, port or host name that looks like a status code (for example `550mail.example`) is retried instead of being read as a hard bounce that fails and suppresses the recipient; the classification is stored on the delivery group (`failureKind`, `failureCode`) and the queue uses it instead of re-parsing the message. A send with neither an HTML nor a text body (after the template) is refused with `422 BODY_REQUIRED` (SMTP `550`) instead of queuing an empty email. SMTP submission and the inbound receiver MIME-parse the raw bytes instead of decoding them as UTF-8 first, which corrupted 8-bit parts in other charsets such as ISO-8859-1. SMTP submission refuses a message with attachments (`550 Attachments are not supported`) instead of delivering it without them. Docs: `docs/emails.md`, `docs/api.md`, `docs/smtp-submission.md`.
- **jsonb columns store real JSON (#261).** Every `jsonb` value written through the `drizzle-orm/bun-sql` adapter was stored as a jsonb *string* holding the JSON text (`jsonb_typeof = 'string'`): Drizzle stringified the value and Bun's driver encoded that string again. Reads looked right, but SQL containment (`@>`), key and path operators and jsonb indexes matched nothing (#226 had to filter webhook events in JavaScript because of it). A `jsonb` column type in `src/db/jsonb.ts` now hands the value to the driver as is, for `webhooks.events`, `api_keys.allowed_senders`, `templates.variables`, `emails.delivery_state` and `webhook_deliveries.last_response_body`; migration `0022` (applied on boot, data only, idempotent) rewrites existing rows as the arrays and objects they encode. Reads also accept rows still in the old form. No schema change, nothing to configure. Query code builds JSON with `jsonb_build_array(...)` from plain parameters, since a stringified parameter cast to `::jsonb` is double-encoded the same way.
- **SPF verification evaluates the record for this server, and every boot checks reverse DNS (#247, #248).** **Verify** marked SPF as verified whenever any `v=spf1` record existed, including `v=spf1 -all`, a Google Workspace or Microsoft 365 record that does not include this server, two records (a permerror that also breaks the domain's other senders), more than 10 lookups, and the dashboard's own `<YOUR_SERVER_IP>` placeholder pasted as is. SPF is now verified only when the domain publishes exactly one record that gives `pass` for every sending IP, evaluated in strict RFC 7208 mode with [mailauth](https://github.com/postalsys/mailauth) (includes, redirects, macros, lookup limits), and the verify response carries `spfReason`. The sending IPs are the new optional `MAIL_PUBLIC_IP` (comma-separated; anything else refuses to boot) or the A/AAAA records of `MAIL_HOSTNAME`. The dashboard suggests `v=spf1 a:<MAIL_HOSTNAME> -all` with a note to merge it into an existing record. Each boot now checks forward-confirmed reverse DNS for those IPs (the PTR must name `MAIL_HOSTNAME`, which must resolve back; Gmail rejects mail without it) and logs the result; it is never fatal. **New dependency:** `mailauth` 7.1.1 (MIT, by the Nodemailer author, pinned exactly). Domains verified before this release keep their stored flag until the next **Verify**. Docs: `docs/domains.md`, `docs/api.md`, `docs/self-hosting.md`, `.env.example`.
- **Sending from a domain with unverified DNS records is no longer silent, and refused sends are no longer masked 500s (#245).** A send from a registered domain whose DKIM, SPF or DMARC record was not verified was queued with only a server log line in production, and nothing at all in development, although mail signed with an unpublished DKIM key fails authentication at the receiver. `POST /api/v1/emails/send` now returns a top-level `warnings` array next to `data` (`dkim_unverified`, `spf_unverified`, `dmarc_unverified`, or `domain_unregistered` in development; `[]` when all records are verified), the dashboard send flash names the records in plain words, and every such send logs `Email queued from a sender domain with unverified DNS records` at `warn` with the email id (SMTP submission's only channel). An unregistered sender domain in production, an unknown template and a missing subject threw plain errors that the API answered as `500 Internal server error`; they are now `422 SENDER_DOMAIN_NOT_REGISTERED`, `404 TEMPLATE_NOT_FOUND` and `422 SUBJECT_REQUIRED` (SMTP `550`), and the template message no longer echoes the submitted id. `.env.example`, `README.md` and `docs/smtp-submission.md` claimed production required DKIM-verified domains, which the code never enforced; they now describe the actual rule. **API change:** the send response gains `warnings`; integrations that matched the old 500 must handle the new codes. Docs: `docs/api.md`, `docs/emails.md`, `docs/dashboard.md`, `docs/smtp-submission.md`, `README.md`, `ARCHITECTURE.md`, `.env.example`.
- **Retries no longer reach recipients suppressed after the email was accepted (#262).** The suppression list was checked once, when the email was accepted, but temporary failures are retried for up to `MAIL_RETRY_MAX_AGE_HOURS` (48 h): a recipient who unsubscribed, complained or hard-bounced on another email in the meantime still got this one. Each retry pass now re-checks every recipient still pending against the sending key's suppression list; suppressed ones are dropped, the others still sent, and a group left with nobody fails without sending. Docs: `docs/emails.md`.
- **The send queue no longer opens unbounded connections when receivers are slow (#176).** The queue polled every 2 seconds on a fixed timer without waiting for the previous poll's sends, and each poll claimed 5 more rows; with a slow or hanging receiver (SMTP timeouts reach 10 minutes) the number of sends in flight grew without limit, exactly when backing off matters. Polls are now scheduled one after another and never overlap, and each claims only as many rows as there are free slots under the new `QUEUE_MAX_CONCURRENT_SENDS` (default `10` per process); when all slots are taken it claims nothing. A slow send holds one slot rather than the whole batch. The poll interval and batch size are now configurable (`QUEUE_POLL_INTERVAL_MS`, default `2000`; `QUEUE_BATCH_SIZE`, default `5`), and polls carry +/-10% jitter so replicas don't hit the database in lockstep. The webhook delivery worker gets the same non-overlapping, jittered poll. An unexpected error in one send is now logged (`Email send attempt crashed`) instead of being dropped. New optional env vars, all validated at boot (a value that is not a whole number in range refuses to start). No migration, no new dependency. Docs: `docs/emails.md`, `docs/webhooks.md`, `docs/self-hosting.md`, `ARCHITECTURE.md`, `.env.example`.

### Security

- **Implicit TLS submission: a client hanging up can no longer pin a CPU core (#351).** On the implicit-TLS port (465, #349), every session the server ended (on `QUIT`, a `421` or the idle timeout) left the TLS socket half-closed under Bun, and once the client's FIN arrived the socket stayed in `CLOSE_WAIT` for good: nothing, `destroy()` included, could close it, and Bun's event loop spun on it at a full CPU core on Linux (on macOS the descriptor leaked). Anyone who could reach the port could starve the server by connecting, sending `QUIT` and hanging up. The listener now never half-closes a TLS socket: ending our side closes the whole socket once the last reply is written, and a client's FIN or a socket error closes it at once, at every stage. Also, the handshake timeout no longer outlives the handshake (it destroyed idle sessions before smtp-server could send its `421`). Plaintext submission and inbound SMTP on port 25 were not affected. Integration tests hang up at each stage and assert that no socket is left and the process goes back to idle.
- **Template variables are HTML-escaped in the HTML body (#250).** `{{name}}` inserted its value raw into the HTML body, so an app passing a user-supplied value (a display name, a comment) let anyone inject markup, such as a fake link or form, into mail DKIM-signed for the domain. In the HTML body `{{name}}` is now escaped (`&`, `<`, `>`, `"`, `'`), and the new `{{{name}}}` inserts a value as is for callers that pass HTML on purpose; subjects and text bodies are not HTML and are unchanged. The dashboard preview understands both forms. **Behaviour change:** a template that relies on HTML inside a `{{variable}}` must switch that placeholder to `{{{variable}}}`. Docs: `docs/templates.md`.
- **Error replies no longer carry internal error text, and domain names are case-insensitive.** SMTP submission answered every unexpected failure (a database error, a bug) with SMTP `550` and the raw error message, and four dashboard forms (send, template create and update, webhook create) put the raw message into the redirect URL of their error flash, where a database error's text (the query and its bound values, such as template HTML) landed in browser history and proxy logs. Unexpected submission failures now get a fixed `451 Local error in processing, try again later` (temporary, so the client retries) and expected refusals (sender or recipients missing, headers naming nobody in the envelope, a message that does not parse, allowed senders, inactive key) keep a `550` with a fixed message; dashboard flashes show only messages written for the user. Domain names were matched case-sensitively: `From: x@Example.com` was "not registered" in production and `Example.com` could be registered next to `example.com`. Names are now stored lowercase, every lookup ignores case (also for older rows), and a duplicate in any case gets `409 DOMAIN_ALREADY_REGISTERED` instead of a masked `500`. Docs: `docs/api.md`, `docs/smtp-submission.md`.
- **A DKIM key that does not decrypt no longer sends mail unsigned (#244).** A wrong `DKIM_ENCRYPTION_KEY` (a regenerated `.env`, or a rotation that skipped re-encryption) removed DKIM from every domain at once while the dashboard still showed it as verified; the only signal was one error line per send, and Gmail, Yahoo and Microsoft bulk rules require DKIM. In production BunMail now refuses to start when any stored DKIM key does not decrypt, naming the domains, and the queue never sends unsigned: such an email is held on the retry backoff (#180) and fails with `email.failed` once it is too old to retry, so fixing the key within `MAIL_RETRY_MAX_AGE_HOURS` still delivers it. Inbound notifications from such a domain are not sent. Development keeps sending unsigned, with a warning. Nothing to configure. Docs: `docs/domains.md`, `ARCHITECTURE.md`, `SECURITY.md`.
- **No third-party or inline script on any page, and a CSP that enforces it (#255, part 2).** Every page loaded the Tailwind Play CDN script from `cdn.tailwindcss.com`, including the login, setup, invitation and reset pages while a password or a one-time token was in the DOM, and ran 20 inline scripts and 26 inline `onclick` / `onsubmit` / `onchange` handlers. The stylesheet is now built with the Tailwind v4 CLI (`bun run build:css`, new dev dependencies `tailwindcss` and `@tailwindcss/cli`) from `src/pages/assets/dashboard.input.css`, and every behaviour lives in one hand-written file, `src/pages/assets/dashboard.js`, wired by `data-*` attributes. BunMail serves both at `/dashboard/assets/` with a content-hash `?v=` and a one-year `immutable` cache. The landing page, the dashboard and the HTML 404 page now send `Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: https:; font-src 'self'; connect-src 'self'` plus the part 1 baseline; the API and the OpenAPI docs at `/api/docs` keep the baseline. `style-src 'unsafe-inline'` is kept for the email preview (a `srcdoc` iframe inherits the policy, and email HTML uses inline styles); a previewed email's plain `http:` images, remote fonts and remote stylesheets no longer load. The pages keep their v3 look (the v4 compatibility base styles, v3's palette, font stack and `dark:` selector; `outline-none` became `outline-hidden`, `flex-shrink-0` became `shrink-0`). `bun run lint:xss` now fails on any event-handler attribute, inline `<script>` or Tailwind CDN reference under `src/pages`. The stylesheet is a build artefact: the Docker image builds it in a new `css` stage, `bun run dev` builds it before starting, and `bun run dev:css` rebuilds it on change; when it is missing the pages render unstyled and the log says `Dashboard asset missing`. A cancelled confirmation no longer leaves the form's button stuck on "Processing…". Docs: `docs/dashboard.md`, `THREAT_MODEL.md`, `ARCHITECTURE.md`, `docs/self-hosting.md`, `README.md`, `CONTRIBUTING.md`.
- **The app port is published on loopback only, and host-specific compose settings move to an untracked override (#205).** `docker-compose.yml` published the HTTP API and dashboard on all interfaces (`0.0.0.0:3000`), and Docker-published ports bypass UFW, so any install without a firewall rule served plain HTTP to the internet next to its TLS proxy (one production host was). It now publishes `127.0.0.1:${PORT}` only; put a reverse proxy in front (`docs/self-hosting.md`, section 6). `docker-compose.override.yml` is no longer tracked: copy `docker-compose.override.example.yml` (git-ignored copy, one per host) for loopback Postgres in development, inbound SMTP on 25, SMTP submission, the TLS mount, or (not recommended) exposing the app without a proxy via `ports: !override` (Compose 2.24.4 or later). Hosts no longer carry local edits to tracked compose files, so `git pull` stops conflicting with them. The startup hints for inbound SMTP and submission now point at the override. **Upgrade:** before pulling, save your edits and restore the tracked files: `cp docker-compose.override.yml ~/compose-override.bak 2>/dev/null; git diff docker-compose.yml > ~/compose-edits.diff; git checkout -- docker-compose.yml docker-compose.override.yml`; then pull, and recreate `docker-compose.override.yml` from the example with the ports and mounts this host needs (`docker compose config` shows the result). Development setups lose the Postgres port until they copy the example. If you reached port 3000 directly without a proxy, add the `!override` block from the example. Docs: `README.md`, `docs/self-hosting.md`, `docs/inbound.md`, `docs/smtp-submission.md`, `ARCHITECTURE.md`.
- **Security headers on every response (#255, part 1).** The dashboard sent no security headers except on its public auth pages. Every response now carries a baseline `Content-Security-Policy` (`object-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'`: no plugins, no `<base>` rewriting, forms only to this origin, no framing by other sites), `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY` and `Referrer-Policy: same-origin`; every `/dashboard` response is `Cache-Control: no-store`, so pages with mail, keys or one-time secrets stay out of browser and proxy caches; `Strict-Transport-Security: max-age=31536000` (no `includeSubDomains`) is added when `APP_BASE_URL` is `https://`. Nothing the dashboard does today is blocked. Still to come in part 2: self-hosted CSS instead of the Tailwind CDN script, the inline scripts moved to a served file, and `script-src` / `style-src` in the CSP. No new dependency. Docs: `docs/dashboard.md`, `THREAT_MODEL.md`, `ARCHITECTURE.md`.
- **Webhook signing secrets are encrypted at rest (#259).** They were stored in plaintext while DKIM keys were already encrypted, so anyone with a database dump or backup (but not the `.env`) could sign requests every receiver accepts as genuine, such as fake `email.bounced` or `email.received` events. They now use the same AES-256-GCM `v1:` format and `DKIM_ENCRYPTION_KEY` as DKIM keys: encrypted on create, decrypted only by the delivery worker, and a secret that no longer decrypts fails the attempt without sending rather than signing with the wrong value. On the first boot, existing secrets are encrypted in place (`Encrypted webhook signing secret at rest`, once per webhook; `src/db/encrypt-webhook-secrets.ts` can also be run by hand). Migration `0021` (applied on boot) widens `webhooks.secret` to `varchar(255)`. Receivers keep their secret: nothing changes for them. Key rotation now has to re-encrypt webhook secrets too (`SECURITY.md`). No new dependency. Docs: `SECURITY.md`, `THREAT_MODEL.md`, `docs/webhooks.md`, `ARCHITECTURE.md`, `docs/self-hosting.md`, `.env.example`.
- **Log hygiene: no webhook credentials, seed keys, query parameters or quoted recipients in logs (#260).** Webhook URLs are logged as their origin only (scheme, host and port): services such as Slack and Discord put the credential in the path, so log access was enough to post to those channels. The seed script prints the new admin API key straight to the terminal instead of through the structured logger, so seed output shipped to a log system (CI, a Kubernetes Job) no longer carries a full key. The logger's safety net now also cuts the bound values from any drizzle query error message (`Failed query: <sql>\nparams: [REDACTED]`), wherever a call site logs `error.message`; those values can be account emails, token hashes or an encrypted DKIM key (for example a failed dashboard domain insert). With `LOG_REDACT_PII` on, the suppressions list filter and the email addresses quoted in remote SMTP replies on `MX group send failed` are masked like any other address. Nothing to configure, no new dependency. Docs: `docs/logging.md`, `docs/self-hosting.md`.
- **SMTP submission: the daily quota is exact, and a valid key no longer resets the failed-AUTH count (#190).** The per-key daily quota read the day's count, parsed and queued the message, and only then recorded it, so concurrent sessions (or replicas) could all pass a count of `quota - 1` and overshoot the cap. Each message now takes its slot before the send in one atomic statement (`accepted + 1` only while below `SMTP_SUBMISSION_DAILY_QUOTA`); a message rejected after that hands the slot back and is counted as rejected. A successful AUTH used to clear the IP's failed-AUTH counter, so anyone holding one valid key could fail up to the limit, log in once, and keep guessing at other keys indefinitely; failures now expire only with their window. Nothing to configure, no migration, no new dependency. Docs: `docs/smtp-submission.md`, `THREAT_MODEL.md`.
- **Dashboard login throttle: signing in no longer resets an address's failures, and IPv6 clients are counted per /64 (#256).** The login counts every attempt before the password check, and a successful login used to clear the client address's counter; since invite-only accounts (#217), anyone with an account of their own could fail up to the limit, sign in once, and keep guessing at another account's password from the same address indefinitely. A success now gives back only its own attempt; earlier failures stay until the window ends, and repeated successful logins still never lock anyone out. IPv6 clients were keyed by full address, so one client could rotate through its `/64`; they are now counted per `/64` (login and the ownership transfer check), and an IPv4-mapped address counts as its IPv4. When `DASHBOARD_TRUSTED_PROXY_HOPS` is set but a request arrives with fewer `X-Forwarded-For` entries, BunMail logs `Request bypassed the trusted proxy` (at most once an hour): the app is reachable directly and the header can be forged, so bind its port to loopback or firewall it. Deliberately not added: a global failure budget across addresses, which would let anyone lock every account out (see `THREAT_MODEL.md`). The timing-safe password compare item of #256 went with the shared dashboard password in #216. Nothing to configure, no new dependency. Docs: `docs/dashboard.md`, `docs/self-hosting.md`, `ARCHITECTURE.md`, `THREAT_MODEL.md`.

## [0.10.0] - 2026-10-18

### Upgrade guide (from 0.9.x)

0.10.0 replaces the shared dashboard password with accounts and adds two production boot guards. A production deploy (`BUNMAIL_ENV=production`, which `docker-compose.yml` always sets) refuses to start until `.env` is updated, so follow these steps in order. The REST API, SMTP and the queue keep working once the new version is up; only the dashboard waits for the owner account to be claimed (step 6).

1. **Back up the database** before pulling, for example `docker compose exec db pg_dump -U bunmail bunmail > bunmail-before-0.10.sql` (use your `POSTGRES_USER` / `POSTGRES_DB` if you changed them). Eight migrations run on the first start (step 5), two of which change data.
2. **Add the required settings to `.env` before pulling:**
   - `BUNMAIL_OWNER_EMAIL=you@yourcompany.com` (#215): the dashboard owner account, one bare address of at most 254 characters. Required in production; a malformed value is refused in every environment.
   - `MAIL_HOSTNAME=mail.yourcompany.com` (#242): this server's fully qualified hostname, matching the sending IP's PTR record. Production refuses an unset value, `localhost`, an IP address, a single-label name, an invalid hostname and placeholder or reserved names (`example.com`, `yourdomain.com`, `.test`, `.invalid`, `.local`, `.localhost`).
   - `APP_BASE_URL=https://mail.yourcompany.com` (no trailing slash): optional, but every link BunMail builds comes from it: the owner setup link, invitation links, password reset links and the "view in dashboard" link of inbound notifications. Unset or not an `http(s)://` URL, the setup and reset links point at `http://localhost:PORT` and no invitation is ever emailed (the inviter sees the link instead).

   Without `BUNMAIL_OWNER_EMAIL` or a usable `MAIL_HOSTNAME` the container stops at boot with a `[config]` error that names the variable, before any migration runs, and restarts in a loop until it is fixed.
3. **Review the new optional settings** (all have defaults, see `.env.example`):
   - `SYSTEM_MAIL_FROM` (#217): sender of invitation emails, one bare address on a domain registered and DKIM-verified in BunMail. Unset, the inviter copies each link from the dashboard. A malformed value refuses to boot.
   - `INVITE_EXPIRY_DAYS` (#217): how long an invitation link stays valid, a whole number of days from 1 to 90 (default `7`); anything else refuses to boot.
   - `API_RATE_LIMIT_MAX` / `API_RATE_LIMIT_WINDOW`: the per-API-key rate limit is now actually enforced, 100 requests per 60 seconds by default, then `429` with `Retry-After`. Raise it before upgrading if one key legitimately makes more calls. A value that is not a positive integer refuses to boot.
   - `MAIL_RETRY_MAX_AGE_HOURS` (#180, default `48`): how long temporary delivery failures are retried with backoff.
   - `MAIL_ALLOW_PRIVATE_MX` (default `false`): delivery now refuses MX hosts on private, loopback or link-local addresses. Set `true` only if you deliver to an internal mail server on purpose.
4. **Check local edits and the non-root container.** `docker-compose.yml` (sysctl for non-root binding #167, log rotation #284) and `docker-compose.override.yml` (#209) changed: if you edited them, `git stash` before pulling and `git stash pop` after. The container now runs as uid 1000 (#167): a TLS private key mounted for `SMTP_SUBMISSION_TLS_KEY` must be readable by uid 1000, and if your platform forbids the `net.ipv4.ip_unprivileged_port_start` sysctl, run the SMTP listeners on high ports inside the container (`docs/self-hosting.md`, Runs as non-root).
5. **Pull and rebuild:** `git pull && docker compose up -d --build`. The container applies the new migrations on start (several replicas wait for one another, #175):
   - `0013`: `emails.reply_to` (#169).
   - `0014`: deletes webhook deliveries that reached another API key's webhook (data only, #226).
   - `0015`: retry backoff and leases, `emails.next_attempt_at`, `locked_by`, `lease_until` (#180); rows left in `sending` get a 15-minute lease.
   - `0016`: the account tables `users`, `user_credentials`, `sessions`, `user_tokens` (#214).
   - `0017`: session token rotation, `sessions.previous_token_hash`, `sessions.rotated_at` and the `session_token_history` table (#216).
   - `0018`: the `user_tokens_invite_check` constraint (#217).
   - `0019`: `sessions.credential_id` (#277).
   - `0020`: `created_by_user_id` on `api_keys`, `templates`, `domains` and `webhooks`, and `api_keys.disabled_reason` (#219).

   Compose recreates the containers whose definition changed, including for the new log rotation (at most 5 files of 10 MB each, #284), so Postgres may restart once as well.
6. **Claim the owner account.** The first boot creates the owner for `BUNMAIL_OWNER_EMAIL` and logs a one-time link: `docker compose logs app | grep 'Owner setup link'`. Open it within 24 hours and choose a password of 15 to 256 characters; setup signs you in. Until setup is done every restart logs a new link and only the most recent one works; for a lost or expired link run `docker compose exec app bun run src/db/reset-owner.ts`, which prints a fresh one to your terminal. Claim it promptly: anyone who can read the logs can use the link first. Every 0.9.x dashboard cookie is rejected, so everyone is signed out once (#216).
7. **Remove `DASHBOARD_PASSWORD` and `SESSION_SECRET` from `.env`** (#216), then `docker compose up -d` (a restart does not re-read `.env`). They no longer do anything; while they are set, every boot logs `Dashboard auth env vars are no longer used since #216, remove from .env`.
8. **Existing records now belong to the owner (#219).** On the first boot every existing API key, template, domain and webhook is assigned to the owner, logged once as `Records without a creator assigned to the owner` with the counts; nothing to configure. Deactivating, removing or demoting an account only reaches the keys that account created, so once you invite teammates (**Invitations** in the dashboard), rotate any admin key you shared with them: create a new key per person from their own account, then revoke the old one.
9. **Check that Postgres was not public (#209).** Before 0.10.0 a plain `docker compose up` published Postgres on `0.0.0.0:5432`, which bypasses UFW. After step 5, `ss -ltnp | grep 5432` should show `127.0.0.1` (or nothing, when you start production with `docker compose -f docker-compose.yml up -d --build`). If the port was reachable from the internet before, consider rotating `POSTGRES_PASSWORD`.
10. **Tell API users and update log tooling.** Behaviour changes they may notice:
    - More than 100 calls a minute on one key now gets `429` (step 3).
    - `email.received` webhooks owned by restricted keys stop receiving events; recreate them under an admin key if that was intended.
    - Invalid request bodies get `422 VALIDATION_ERROR` (malformed JSON `400 INVALID_BODY`) instead of `500`; template variable names are limited to word characters; `limit` above 100 on the tombstones and webhook deliveries lists returns `422`; addresses with empty domain labels, a trailing dot or no dot in the domain are rejected.
    - Every log line now carries `requestId`, `jobId` or `smtpSessionId`, each HTTP request writes one `HTTP request` line (#284), and log messages that contained em dashes were reworded: update log queries and alerts that match on message text.

- **Post-mortem logging: correlation IDs, one line per unit of work, central secret redaction (#284).** Every log line now carries the ID of the work it belongs to, automatically, down to the deepest service call: `requestId` for HTTP requests (returned as `X-Request-Id`; a well-formed incoming `X-Request-Id` from a reverse proxy is reused), `jobId` for each queued email attempt, webhook delivery and purge cycle, `smtpSessionId` for each inbound or submission SMTP connection. - **Account login with revocable server-side sessions (#216, part of #225; supersedes #186, and the dashboard side of #183 and #185).** `/dashboard/login` now takes an email and a password, checked against the owner account (`user_credentials`, argon2id); every failure (unknown email, no password, disabled account, wrong password, over-long input) gets the same `Invalid email or password.` and runs exactly one argon2id verify, so neither the response nor its timing reveals whether an account exists. The reason is logged server-side only (`Dashboard login failed`). A login opens a row in `sessions`; the `bm_session` cookie carries an opaque 256-bit token whose SHA-256 is all the database stores. Sessions expire after 24 hours idle and 7 days after login at the latest (database clock), work across replicas, and are revoked for real: **Log out** deletes the row, completing owner setup deletes the owner's sessions and opens a new one in the same transaction, and `reset-owner` signs the owner out everywhere as soon as it runs. **Token rotation with reuse detection:** after 60 seconds of use a session's token is replaced (that write is also the idle refresh), the replaced token keeps working for 30 seconds for requests already in flight, and presenting it later revokes every session of the user and logs `Session token reuse detected: all sessions of the user revoked` at `warn`. Every replaced token is remembered until the session ends (new `session_token_history` table), so a copied cookie is detected as soon as either side presents a superseded token, however old, including a thief who keeps the stolen session active while the real user is idle. - **Owner bootstrap from `BUNMAIL_OWNER_EMAIL` (#215, part of #225).** On boot BunMail creates the single dashboard owner for that address (stored lowercased) and logs a one-time setup link at `warn`, or `error` when `LOG_LEVEL=error` (`Owner setup link`, built from `APP_BASE_URL`, or `http://localhost:PORT` when it is unset or not an `http(s)://` URL). ### Fixed

- **The DMARC report sender heuristic matches the real address, not substrings of the header.** `looksLikeDmarcReport` tested known reporters (`enterprise.protection.outlook.com`, `noreply-dmarc-support@google.com`, `dmarc-support@`, ...) with unanchored regexes over the whole `From:` value, so `x@enterprise.protection.outlook.com.evil.example` or a display name quoting a reporter address matched (found by CodeQL's `security-extended` suite, enabled in #230). The sender address is now parsed (the `<...>` part wins) and matched by exact address, exact domain or subdomain, and whole local part. The heuristic only decides whether a message is tried as a DMARC report (the XML is validated afterwards), so the impact was limited to misclassification.
- **A blocklisted or unauthenticated sender no longer suppresses good recipients (#246).** Any `5.x.x` reply counted as a hard recipient bounce, so when a receiver rejected the *sender* (`550 5.7.1 ... blocked using Spamhaus`, a DMARC failure, poor IP reputation), every recipient was permanently suppressed. These replies are now classified as `policy`: the group fails without retrying, nobody is suppressed, its delivery state carries `blocked: true`, and `email.failed` includes `blocked: true`. A reply that also says the user doesn't exist is still a hard bounce. Also, an IP address or port inside a network error (`connect ECONNREFUSED 5.6.7.8:25`) was read as an SMTP status and could suppress the recipient; those are network errors again and are retried.
- **Domain unsubscribe settings are saved and can be edited (#243).** `POST /api/v1/domains` validated `unsubscribeEmail` and `unsubscribeUrl` but never passed them on, so they were silently dropped, and there was no way to set them later. They are now stored on create, editable with the new `PATCH /api/v1/domains/:id` (omit to keep, `null` to clear) and from the domain page in the dashboard, and `unsubscribeUrl` must be `https://` (RFC 8058 one-click).
- **`List-Unsubscribe-Post` is now covered by the DKIM signature (#241).** Nodemailer's default signed-header list includes `List-Unsubscribe` but not `List-Unsubscribe-Post`, and RFC 8058 one-click unsubscribe (which Gmail and Yahoo rely on for bulk mail) only counts when both are signed. BunMail now passes its own list: nodemailer's defaults plus `List-Unsubscribe-Post` and `Feedback-ID`. Verified by signing a real message and reading the signature's `h=` tag.
- **Temporary delivery failures are retried with backoff instead of within seconds (#180).** A 4xx reply or connection error put the email straight back in the queue, so the next 2-second poll took it again: the three attempts were used up within seconds and the email was marked `failed`. Greylisting and provider rate limits (Yahoo `421 [TSS04]`, Microsoft `451 4.7.500`, Gmail `421 4.7.28`), which expect a retry minutes or hours later and are routine for a new sending IP, became permanent failures. Emails now wait 5 m, 15 m, 30 m, 1 h, 2 h, then every 4 h between attempts (new `next_attempt_at` column, migration `0015`), until they are `MAIL_RETRY_MAX_AGE_HOURS` old. Each retry pass also re-checks that the sending API key is still active, and `sentAt` records when the first MX group was delivered.
- **A restarting replica no longer resends other replicas' emails (#180).** Every boot reset all `sending` rows to `queued`, including rows another replica was in the middle of sending, so those recipients got the email twice. Claims now carry a lease (`locked_by`, `lease_until`) that the worker renews while sending; a row is reclaimed only once its lease has expired, and a worker only writes an outcome for a row it still holds. Rows already in `sending` at upgrade get a 15-minute lease from the migration, rows an old replica claims afterwards are treated as leased until 15 minutes after their last update, and a shutting-down process hands its in-flight rows back immediately. An inbound bounce for an email that is still being retried no longer marks it `bounced`, which used to stop its other recipients' retries.
- **Concurrent migration runs crashed a replica (#175).** Every app container runs the migrator on start, and nothing limits BunMail to one replica, yet the runner assumed it ran alone. Two concurrent runs against a fresh database reliably crashed one of them (5 out of 5 trials) with a duplicate-key error in `pg_type`, from the racy bootstrap `CREATE TABLE IF NOT EXISTS`. The run now holds a Postgres advisory lock, taken before the bootstrap, on a single pinned connection (a pooled connection could have taken the lock on one session and run the migrations on another). The second replica waits, then finds every migration applied. The lock is released on success and on failure.
- **Pagination could 500 or read whole tables (#172).** Ten list routes parsed `page`/`limit` with a bare `parseInt`. On the real driver, `?page=0` or a negative page produced a negative `OFFSET` (**500**), and `?limit=abc` or a huge limit returned **every row**, because a `NaN` limit is treated as no limit. The 2 affected API routes (`GET /api/v1/emails/tombstones`, `GET /api/v1/webhooks/:id/deliveries`) now validate like the other list endpoints: invalid values return **422**. The 8 dashboard list pages clamp bad values through a shared `parsePagination()` helper instead of erroring. Testing also showed that a huge `page` (e.g. `1e20`) overflowed Postgres's `OFFSET` and returned 500 on **every** API list route, including ones that looked correct. `page` is now capped at **1,000,000** on all 8 API list routes (422 above it) and in the dashboard helper. **Behaviour change:** API clients sending `limit` above 100 to the tombstones or deliveries endpoints now get 422, matching the rest of the API.
- **Docker healthcheck probed a hardcoded port 3000 (#206).** With a custom `PORT`, the container served traffic normally but was reported **unhealthy** forever, breaking `depends_on: condition: service_healthy`, restart policies and orchestrator health gates. The `HEALTHCHECK` now probes `PORT` (default `3000`). Verified on a real image: `PORT=3300` and the default port both reach `healthy`, and the check still fails when nothing is listening.

### Security

- **Webhook deliveries connect to the address validated by the SSRF guard.** Each delivery attempt resolves the webhook host once, checks every address, and sends the request to the validated address; if the request cannot be built for exactly that address, the attempt fails. The receiver still gets its own host name in the `Host` header and as TLS SNI, and the certificate is checked against that host name before the request is sent. Each attempt uses a fresh connection. The address check now recognizes an IPv4 address embedded in an IPv6 address in every form (IPv4-mapped, IPv4-compatible, NAT64 and 6to4, dotted or hex notation) and judges it by the IPv4 rules, and also refuses IPv6 site-local, multicast and local-use NAT64 addresses and scoped (zone id) answers; this applies to webhooks and outbound MX delivery. Refusal messages no longer include the resolved address. A public IPv6 literal URL (`https://[2001:db8::1]/`) is now validated like an IPv4 literal instead of being refused as unresolvable. Nothing to configure, no new dependency. Docs: `docs/webhooks.md`, `THREAT_MODEL.md`.
- **One-time secret reveals are bound to their creator (#280).** The token that shows a newly created API key or webhook secret once can now be redeemed only by the same user and session, and only on the matching page (an API-key token shows nothing on the webhooks page, which members can open since #222). Any other presentation looks like an unknown token, is logged with IDs only, and leaves the reveal for its creator. Closes the gap before invitations (#217) add other accounts.
- **Dashboard sessions can be revoked, and a stolen cookie stops working quickly (#216).** The old cookie was a stateless HMAC of a timestamp: logout only cleared it in the browser, a copied cookie stayed valid for 24 hours, and the only kill switch was rotating `SESSION_SECRET`. Sessions are now database rows: logout, owner setup and `reset-owner` delete them, tokens are stored only as SHA-256 (a database dump yields no usable cookie, and logs carry only the `ses_` id), tokens rotate every minute with reuse detection that signs the account out everywhere, and a disabled user's sessions stop working at once. Login and logout require same-origin (no login CSRF, no forced logout from another site), a login revokes the session the browser already presented (no session fixation), and a database error in the guard answers `503` instead of letting the request through. Session and login queries go through the same error sanitizer as the owner paths (`UserStoreError`, SQLSTATE only, renamed from `OwnerStoreError`), so token hashes and emails never reach the logs. **No timing-safe compare is left, by design:** the presented token is hashed and looked up through a unique index, and argon2id verification is constant-time inside Bun, so there is no secret compared byte by byte in JavaScript; the `timingSafeEqual` spy test went with the code it tested. Still open, documented in `THREAT_MODEL.md`: login throttling is per IP only (no per-account lockout), the in-memory login limiter and the one-time reveal store are per replica, and the reveal store was not yet bound to a session (fixed by #280 in this release, see above).
- **Recipient address checks are linear, and addresses are capped at 254 characters.** The address regex in `src/utils/recipients.ts` (also used in a simpler form for inbound `MAIL FROM`) allowed dots on both sides of its literal dot, so a malformed address with many dots made it backtrack quadratically (about 7 s at 100 KB). REST callers were bounded by the 1000-character field cap, but the SMTP submission server stored header addresses with no per-address limit and the queue worker then ran the regex on them, so one submitted message could stall the process for seconds or longer. The regexes now exclude the dot from domain labels (no overlap, linear time), addresses over 254 characters (RFC 5321) are dropped before any regex runs, and the submission server drops over-long header addresses at ingestion with a warning. Bounded-time tests now cover every parser on the inbound path (#232). **Behaviour change:** addresses with empty domain labels (`a@b..c`), a trailing dot, or no dot in the domain are now rejected; they were never deliverable.
- **SMTP submission delivers only to envelope recipients.** The submitted message's `To:` and `Cc:` headers were mapped straight to the email's recipients, so every address in them was delivered, whether or not it was sent in `RCPT TO`. One `RCPT TO` plus a `To:` header listing hundreds of thousands of addresses (within the 10 MB message limit) became one accepted submission delivered to all of them, bypassing the 50-recipient cap and the daily quota. `To`/`Cc` now keep only addresses that are also envelope recipients. If the headers name recipients but none of them was sent in `RCPT TO`, the message is rejected with `550` rather than showing the envelope recipients in `To` (which would expose blind recipients to each other).
- **Request bodies are capped, templates can no longer be amplified, and validation errors no longer echo or log the request.** The server used Bun's default 128 MB body limit, and bodies are parsed before authentication, so anyone could make it buffer and parse 128 MB per request; it now rejects bodies over 12 MB with `413` before reading them. Template rendering had no output limit: a template full of `{{a}}` rendered with a long `a` built a multi-gigabyte string in a request handler. Rendering now stops with `422 TEMPLATE_OUTPUT_TOO_LARGE` once a body would pass 5 MB (subject: 500 characters), templates are capped at 5 MB per body and 100 declared variable names (`^\w+$`), and a send accepts at most 100 variables of up to 100 KB. Request validation failures fell through to the generic error path: `500`, with the whole request body (up to the size limit, without authentication) written to the error log. They now return `422 VALIDATION_ERROR` with only the failing paths and fixed messages, and malformed JSON returns `400 INVALID_BODY`; neither is logged as a server error. **Behaviour change:** clients that relied on the `500` for invalid bodies now get `422`/`400`, and template variable names are limited to word characters on create and update.
- **Webhook deliveries that reached the wrong API key before dispatch was scoped are removed on upgrade.** Scoping dispatch to the owning key stopped new leaks, but rows already enqueued for another key's webhook stayed in `webhook_deliveries`: readable and replayable by that webhook's owner, and still delivered while pending. Migration `0014` (data only, applied automatically on boot) deletes outbound-event deliveries whose email belongs to a different key than the webhook (resolved from `emails`, or `email_tombstones` after a purge; rows whose owner can no longer be resolved are deleted too), and `email.received` deliveries held by non-admin keys' webhooks. Legitimate deliveries are untouched.
- **DMARC report endpoints are now admin-only.** `/api/v1/dmarc-reports` used only `authMiddleware`, so restricted (send-only) keys could read every aggregate report for every registered domain: the domain list, reporting organisations, sending source IPs and volumes, SPF/DKIM results and the raw XML. It now uses `adminMiddleware` like the rest of the management plane (`/api/v1/domains`, `/api/v1/inbound`), returning `403 ADMIN_REQUIRED` to restricted keys. The admin-gate integration test now covers every admin-only list route.
- **Revoking an API key now cuts off its webhooks and open SMTP sessions too.** Dispatch and the delivery worker only checked that a webhook was active, not its key, so webhooks registered with a revoked key kept receiving that key's events, and a revoked **admin** key's webhooks kept receiving `email.received` for all inbound mail. The SMTP submission server checked the key only at AUTH, so a session opened before the revocation could keep sending. Dispatch and the worker now require the owning key to be active (queued deliveries for a revoked key end at `failed`), and `createEmail` rejects revoked keys with `InactiveApiKeyError` (SMTP `550`, HTTP `401` `API_KEY_REVOKED`).
- **Webhook responses are now read with a size limit, and a crashing attempt still counts.** The delivery worker read each receiver's full response (`response.text()`) before keeping a 2 KB preview, and `fetch` decompresses responses transparently, so a receiver controlled by any API key could return a small compressed body that expands to gigabytes (in a local test an endless response reached 4.4 GB of memory in 5 s). Since the attempt was only counted after the read, the row was claimed again after a restart and crashed the server again. Reading less is not enough on its own: Bun inflates a compressed body in native code whatever JavaScript reads (a 0.5 MB gzip response cost about 1 GB). The worker now fetches with `decompress: false`, never decodes a compressed body (the preview says `[gzip-encoded response body not shown]`), streams at most 8 KB of an uncompressed one and cancels the rest, and sends `Accept-Encoding: identity`. Each attempt is counted when it is claimed, in the same transaction as the claim's follow-up updates; a row whose attempts never complete ends at `failed` once over the limit.
- **Outbound delivery no longer connects to MX hosts on private addresses.** The mailer connected to whatever host a recipient domain's MX record named. Recipient domains are chosen by API callers and anyone can publish an MX pointing at `127.0.0.1` or an internal network, so any key could aim the server's port-25 connections at internal hosts and read the outcome back through `lastError`. The mailer now resolves each MX host itself, refuses if any address is not publicly routable (same ranges as the webhook SSRF guard) or the domain publishes a null MX, and connects to the checked address (IPv4 preferred, as before) with the MX name as TLS SNI, so the DNS answer cannot change in between. A refused MX is a normal failed attempt for that group. New `MAIL_ALLOW_PRIVATE_MX` (default `false`) allows private MX hosts for deliberate internal delivery.
- **Inbound bounce parsing is now linear-time, and a bounce must match a real recipient.** Every inbound message goes through the DSN parser, unauthenticated. Several parts of it were super-linear in the message size (one regex compiled per address-shaped token and run over the whole body, a `[^]*` content-type expression, and address extraction on unbounded lines), so a crafted message could stall the whole process: in tests, inputs under 1 MB took from 9 s to over a minute. The parser now runs in linear time, with bounded-time regression tests. Separately, a bounce was linked to its email only by Message-ID, which every recipient sees, and the bounced address was never checked, so a forged DSN could suppress any address under the sender's key, mark the email bounced and fire `email.bounced`. The handler now requires `Final-Recipient` or the newly parsed `Original-Recipient` to be one of the email's `to` / `cc` / `bcc` addresses and drops anything else (`dropped-recipient-mismatch`).
- **The per-API-key rate limit is now enforced.** `rateLimitMiddleware` registered its hook without `.as("scoped")`, so Elysia kept it local to the middleware instance and it never ran for the routes of the plugins that `.use()` it: no API route was rate-limited. The e2e suites stub this middleware, so no test noticed. It is now scoped like `authMiddleware`, and an integration test sends requests through a real plugin and asserts the `429`. The limit is now configurable with `API_RATE_LIMIT_MAX` and `API_RATE_LIMIT_WINDOW` (seconds), default 100 per 60 s, validated at boot. **Upgrade note:** clients that make more than 100 API calls a minute on one key now get `429` with `Retry-After`; raise the limit if that is legitimate.
- **Two dashboard pages now escape data that API keys can write.** The templates list rendered each template's `variables` without the `safe` attribute (`@kitajs/html` does not escape children by default), and the suppressions list built its Delete confirmation from the suppressed address inside an inline `onclick`, where attribute escaping does not cover single quotes. The variables cell is now escaped, and the confirmation text is static (every other delete button already used static text). The CI `xss-scan` gate missed the first case: `@kitajs/ts-html-plugin` 4.1.4 only checks the false branch of `cond ? a : b`, and it never checks attribute values. Regression tests in `test/unit/dashboard-xss.test.ts` render both pages with hostile values.
- **Webhook events are now delivered only to the webhooks of the API key that owns the email.** Dispatch used to look up every active webhook subscribed to an event type, whoever owned it, so one API key's `email.sent`, `email.failed` and `email.bounced` events (sender, recipient, subject, message id) were also delivered to other keys' webhooks. `findWebhooksForEvent` now filters by the owning `api_key_id` in SQL, from both the send queue and the bounce handler. Inbound `email.received`, which has no owning key, now goes only to webhooks owned by **admin** keys, and creating a webhook that subscribes to `email.received` with a restricted key returns `403` with `code: "INBOUND_EVENTS_REQUIRE_ADMIN"` (inbound mail is already admin-only, #130). **Upgrade note:** existing `email.received` webhooks owned by restricted keys stop receiving events; recreate them under an admin key if that was intended. Covered by real-Postgres tests that create two keys and assert neither sees the other's events.
- **A plain `docker compose up` published Postgres on `0.0.0.0:5432` (#209).** The tracked `docker-compose.override.yml` (meant for local development) publishes the database port, and Compose merges it automatically; README and `docs/self-hosting.md` told operators to run exactly that. Docker-published ports bypass UFW, so a host firewall didn't stop it, leaving the database internet-reachable behind only `POSTGRES_PASSWORD`. The override now binds `127.0.0.1:5432`, so local development is unchanged. `docs/self-hosting.md` also previously described the port as "internal only"; it now documents the real behaviour and the UFW caveat. **Check existing deployments:** run `ss -ltnp | grep 5432` on the host; if it shows `0.0.0.0` or `*`, pull this change and recreate the stack (or start with `-f docker-compose.yml`), and consider rotating `POSTGRES_PASSWORD`.
- **The container now runs as non-root (#167).** The `Dockerfile` run stage sets `USER bun` (uid 1000, from the `oven/bun` image). An RCE in the app, `mailparser` or the DMARC parser (reachable from unauthenticated inbound mail) no longer lands as root, and the app can't modify its own files. `docker-compose.yml` pins `sysctls: net.ipv4.ip_unprivileged_port_start: 0` so the non-root process can still bind 25 and 587 (Docker 20.10+ already defaults to this; the pin makes it explicit). An SMTP server that can't bind its port now **exits with a clear message** (port, cause, fix) instead of logging and carrying on while the HTTP health check stayed green. **Upgrade notes:** (1) if you mount a TLS private key for `SMTP_SUBMISSION_TLS_*`, it must be readable by uid 1000; (2) if you run on a platform that forbids the sysctl, use high ports inside the container (see `docs/self-hosting.md`); (3) if you edited `docker-compose.yml` locally, `git pull` may refuse until you `git stash` first.
- **Dashboard send form now rejects CR/LF in `cc`, `bcc` and `subject` (#202).** `POST /dashboard/send` validated these as unrestricted strings, while the REST API's `sendEmailDto` caps them and rejects CR/LF as header-injection defense-in-depth (#133). Both entry points into `createEmail` now enforce the same guard. Exposure was limited to an authenticated dashboard operator.
- **Removed 15 stale CVE suppressions from `.trivyignore` (#170).** They covered Go-stdlib CVEs in esbuild binaries, justified until "#56 lands" with a 2026-08-01 revisit date. Both conditions had passed: #56 and #163 removed esbuild, drizzle-kit and the TypeScript binary from the image. Both scans (Trivy v0.74.0, HIGH/CRITICAL) are now verified clean with **no** suppressions: the image contains no Go binaries, and the fs scan skips `node_modules`, so it never matched these entries anyway. Stale entries were a latent risk, since they would have silently hidden those IDs from a real dependency. The file keeps its policy header, and `docs/security-ci.md` now says to remove entries once stale.
- **Inbound DNSBL check skipped most of `172.0.0.0/8` (#166).** The private-IP skip used `startsWith("172.")`, so clients on roughly 240 public `/16` blocks (`172.0` to `172.15`, `172.32` to `172.255`) were never checked against Spamhaus ZEN. It also only skipped the literal `127.0.0.1` and missed link-local and CGNAT. The skip now reuses the numeric range checks from the webhook SSRF guard (`isBlockedIp`), so only genuinely non-public addresses are skipped. Only affects deployments with inbound SMTP enabled (`SMTP_ENABLED=true`).
- **Patched two HIGH `nodemailer` advisories: CVE-2026-90776 (DoS via a crafted email, fixed in 10.0.5) and GHSA-v53p-9fqp-m79j (quadratic backtracking in the address parser, fixed in 10.0.6).** The Trivy fs and image scans had failed on `main` and every PR since 2026-10-05. Bumped `nodemailer` 10.0.3 → 10.1.2, plus `mailparser` 3.9.24 → 3.9.40 and `smtp-server` 3.19.10 → 3.19.23, whose new releases also depend on 10.1.2. That dedupes the tree to one patched copy (the old `mailparser` pinned its own nested 10.0.3), with no `overrides` needed.
- **Trivy HIGH: stack-exhaustion DoS in `deepmerge-ts`: CVE-2026-40345 (#161).** The `Security` workflow had been failing on `main` since 2026-08-21; both the Trivy fs and image scans flagged `deepmerge-ts@7.1.5` (stack exhaustion when merging recursive object graphs, fixed upstream in 8.0.0). Bumping `mailparser` to 3.9.24 pulls `html-to-text@10.0.1`, which requires `deepmerge-ts@^8.0.1` (resolves to 8.0.2), clearing the finding. ### Security

- **Inbound DoS via DMARC report parsing: decompression bomb + XML entity expansion (#129).** A message that looks like a DMARC aggregate report is decompressed and XML-parsed on the **unauthenticated** inbound path (port 25/2525), so one crafted email could take the receiver, and the whole process, down. (1) **Decompression bomb:** the raw message is capped at 10 MB, but a gzip/zip attachment can expand ~1000:1; the previous synchronous `gunzipSync`/`unzipSync` allocated the full output (multiple GB → OOM/freeze). Now inflation uses fflate's **streaming** `Gunzip`/`Unzip`, fed in 64 KB slices and **aborted past a 25 MB output cap**: a real report is far smaller, and a bomb is dropped early. (2) **Billion-laughs:** the XML parser now runs with `processEntities: false` and rejects any input containing `<!DOCTYPE` (RFC 7489 reports never carry one; its only use here is a nested-entity CPU bomb). On any of these the report is dropped and normal inbound storage takes over. Added DoS regression tests (`test/unit/dmarc-parser.test.ts`). Only reachable when inbound (`SMTP_ENABLED`) is on.
- **Codebase-wide XSS-escaping audit + `xss-scan` CI gate (#150).** Following the DMARC XSS fix (#131), audited every dashboard JSX interpolation with `@kitajs/ts-html-plugin`'s `xss-scan` and added the missing `safe` attribute across 23 `src/pages` files, including genuine stored/user-data sinks (email `cc`/`bcc`/`lastError`/`messageId`, tombstone id, template body, domain DNS record fields, webhook events/secret, API-key prefix) and the shared leaf components (`StatusBadge`, `FlashMessage`, `EmptyState`, nav labels, `DetailField`). `@kitajs/html` does **not** auto-escape interpolated children, so each was a latent injection. `xss-scan` now runs in CI (`bun run lint:xss`) and **fails the build on any unescaped child**, so a new XSS sink can't merge silently. Escaping-only: no rendered output changed.
- **Stored XSS in the DMARC dashboard pages (#131).** DMARC aggregate-report fields arrive over the **unauthenticated** inbound path and are stored verbatim (`orgName`, `domain`, `sourceIp`, `disposition`, DKIM/SPF auth domains + results, and the raw report XML). `@kitajs/html` does **not** auto-escape interpolated children, escaping needs the `safe` attribute, and the DMARC list + detail pages omitted it, so an emailed report containing `<img src=x onerror=…>` would execute in the admin dashboard origin (session theft, CSRF against the admin-only endpoints) the moment an operator opened the page. Every attacker-controlled interpolation on both pages now carries `safe`; added a render-level regression test (`test/unit/dmarc-xss.test.ts`). Inbound email *bodies* were already sandboxed (iframe without `allow-scripts`) and are unaffected. A codebase-wide `xss-scan` CI gate + audit of the remaining flagged interpolations is tracked in #150. Only reachable when inbound (`SMTP_ENABLED`) is on.
- **Dashboard & API hardening bundle (#133).** Several defense-in-depth fixes from the v0.8.0 security sweep: (1) the global 500 handler no longer returns the raw `error.message` in production (driver errors could embed table/column/query fragments → schema disclosure); the detail is logged server-side and the client gets a generic `"Internal server error"` (dev keeps the message). (2) The dashboard session cookie now carries **`Secure`** in production (never sent over plaintext HTTP), and every state-mutating dashboard **POST** is checked for a same-origin `Origin`/`Referer` (a **CSRF second layer** beyond `SameSite=Lax`; cross-origin or header-less POSTs get **403**). (5) `cc`/`bcc`/`subject` now reject CR/LF and enforce a length cap (SMTP header-injection defense-in-depth), and CR/LF are stripped from the `List-Unsubscribe` mailto/url. - **One-time secret reveal: stop leaking API keys & webhook secrets via URLs (#132).** The dashboard previously returned a freshly-created raw API key (`bm_live_…`) and webhook HMAC secret by putting them in the post-create redirect's query string (`?…&rawKey=…`, `?…&secret=…`), which leaks them into browser history, reverse-proxy/CDN/access logs, and the `Referer` header of any sub-resource: defeating the "shown once, stored hashed" model. Now the secret is stashed server-side under an opaque 32-byte random token (60s TTL, single-read); only the **token** rides in the redirect URL, and the follow-up GET consumes it once to render the secret. No secret ever appears in a URL. The reveal store is in-memory/per-process (documented caveat: on a multi-replica deploy the operator revokes + recreates if the GET lands on another replica). REST responses are unaffected (the raw key is returned in the JSON body, which is correct). See [THREAT_MODEL.md](THREAT_MODEL.md).
- **Webhook SSRF guard (#128).** Webhook URLs are tenant-supplied and fetched server-side, with the response read back through the delivery API: previously an unvalidated, *exfiltrating* SSRF (register `http://169.254.169.254/…` or `http://127.0.0.1:5432`, get cloud-metadata creds / internal responses back). Now every webhook URL is validated **at creation** (REST + dashboard) **and re-validated before each delivery attempt** (TOCTOU): it must be `https` (set `WEBHOOK_ALLOW_INSECURE_HTTP=true` to also allow `http`), and its host is **DNS-resolved and rejected if any address is private/loopback/link-local/ULA/CGNAT/metadata** (`127/8`, `10/8`, `172.16/12`, `192.168/16`, `169.254/16`, `::1`, `fc00::/7`, `fe80::/10`, v4-mapped, …). Delivery uses `redirect: "manual"`, so a 3xx into an internal address can't bypass the check (it's counted as a failed delivery). Create-time rejection returns **HTTP 422 `WEBHOOK_URL_BLOCKED`**. New env: `WEBHOOK_ALLOW_INSECURE_HTTP` (default `false`).
- **Bump `linkify-it` 5.0.1 → 5.0.2: CVE-2026-59887 (HIGH).** Patches a quadratic-complexity DoS in linkify-it's `mailto:` validator, pulled in transitively via `mailparser`. ### Fixed

- **Queue race condition under concurrent workers.** The poll loop's `queued → sending` transition was a `SELECT` followed by a separate per-row `UPDATE` (`queue.service.ts`), so two workers running it at the same time could pick up the same rows and double-send the same email. The transition is now a single atomic statement: `UPDATE emails SET status='sending', attempts = attempts + 1 WHERE id IN (SELECT id … FOR UPDATE SKIP LOCKED) RETURNING *`. `FOR UPDATE SKIP LOCKED` makes a concurrent caller skip rows another transaction has locked rather than waiting on them or grabbing duplicates, so two workers always see disjoint result sets. We're single-worker today so this wasn't manifesting in production, but it was the blocker for horizontal scaling: running a second BunMail instance behind a load balancer is now safe. New integration test ([test/integration/queue-claim.integration.test.ts](test/integration/queue-claim.integration.test.ts)) seeds 30 queued rows, fires 6 concurrent claim calls, asserts each row is claimed by exactly one caller. (#20)

### Added

- **DMARC `rua` aggregate report ingest.** When BunMail's inbound SMTP receives a DMARC aggregate report (the daily XML attachment that Microsoft / Google / Yahoo / Mail.ru send to the `rua=mailto:` address you publish in `_dmarc`), the new module ([src/modules/dmarc-reports/](src/modules/dmarc-reports/)) detects it via a heuristic on sender + subject + content-type, decompresses the attachment (gzip / zip / raw: sniffed by magic bytes, not filename), parses the RFC 7489 XML via `fast-xml-parser`, and stores the report in two new tables: `dmarc_reports` (one row per report, with `rawXml` kept for forensics) + `dmarc_records` (one row per source IP, FK with `ON DELETE CASCADE`). Re-receipt of the same report is deduped via `UNIQUE (org_email, report_id)` + `ON CONFLICT DO NOTHING`. DMARC-shaped messages **don't pollute** the `inbound_emails` table: they branch off in [smtp-receiver.service.ts](src/modules/inbound/services/smtp-receiver.service.ts) after the bounce branch. Two new REST endpoints: `GET /api/v1/dmarc-reports` (paginated, optional `?domain=`) and `GET /api/v1/dmarc-reports/:id` (with per-source-IP detail), and matching dashboard pages at `/dashboard/dmarc-reports`. The detail view computes alignment totals and highlights misaligned source IPs in amber so spoofing attempts and unauthorised third-party senders are visually obvious. No webhook event for v1 (consumers can poll); no `ruf` / forensic report support; no backfill. See [docs/dmarc-reports.md](docs/dmarc-reports.md). (#41)

Catches `ON DELETE CASCADE` / `SET NULL` behaviour, `ON CONFLICT DO UPDATE` upserts, encryption round-trips, schema drift between TS models and the live DB. (b) New unit tests for every previously-uncovered service (`mailer`, `dns-verification`, `template`, `webhook`, `webhook-dispatch`, `api-key`, `domain`) using mocked dependencies: covers the orchestration code paths even without a DB. Plus 20 JSX render-smoke tests for every dashboard page + presentational component. **Overall coverage uplift: 61.7% → 89.8% functions, 66.1% → 93.0% lines**. `bunfig.toml` threshold raised to `function: 0.85, line: 0.9` so future PRs can't regress. CI provisions a `postgres:16` service container and runs all three tiers on every PR. New scripts: `test:unit`, `test:e2e`, `test:integration`, `test:integration:setup`, `test:all`, `test:coverage`. See [docs/testing.md](docs/testing.md). (#70)

### Added

- **Auto-suppress on inline SMTP 5xx rejections.** When a recipient's MX rejects an outbound send during the SMTP transaction with a `550 5.1.1` (the way Gmail / Outlook / Yahoo handle obviously-bad addresses today), the queue's failure path now classifies the error via [src/utils/smtp-error.ts](src/utils/smtp-error.ts), calls `suppressionService.addFromBounce()` to permanently suppress the recipient, marks the email `status = 'bounced'`, fires the `email.bounced` webhook with `source: "inline"`, and **stops retrying**. Previously the queue would retry three times, hitting the same MX with the same `5.1.1` each cycle: exactly the pattern that tanks IP reputation. Soft 4xx and infrastructure errors keep the existing retry-up-to-`MAX_ATTEMPTS` behaviour. Webhook payload shape matches the async-DSN bounce path from #24: receivers get a uniform `email.bounced` signal regardless of which path fired. Closes the auto-suppression loop for hard bounces that #24 left open. (#68)
- **DSN / bounce parsing.** When BunMail's inbound SMTP receives a Delivery Status Notification, the new bounce module ([src/modules/bounces/](src/modules/bounces/)) parses it (RFC 3464 first, with a heuristic-gated regex fallback for non-RFC bounces from old MTAs), links it back to the original outbound email by `Original-Message-ID`, persists a per-API-key suppression via `suppressionService.addFromBounce()`, marks the original email row's `status` as `bounced`, and fires the `email.bounced` webhook. Hard bounces (5.x.x) become permanent suppressions; soft bounces (4.x.x) become 24-hour time-windowed suppressions and **escalate to permanent on a second soft bounce within the window**: repeated transient failures are effectively permanent for IP-reputation purposes. DSNs without an `Original-Message-ID` are dropped with a warning rather than risk suppressing under the wrong tenant. Bounce-shaped messages are routed via the new branch in [smtp-receiver.service.ts](src/modules/inbound/services/smtp-receiver.service.ts) and **don't pollute** the `inbound_emails` table. See [docs/bounces.md](docs/bounces.md). (#24)
- **Suppression list.** New `suppressions` table + `/api/v1/suppressions` CRUD endpoints (`POST`, `GET`, `GET /:id`, `DELETE /:id`). The list is **per-API-key** (different keys often represent different customer environments: one's bounces shouldn't gate another's sends). `POST /api/v1/emails/send` now runs a gate against the calling key's suppression list before any other work; suppressed recipients return HTTP 422 with `code: "RECIPIENT_SUPPRESSED"` and `suppressionId` so clients can pivot directly to `DELETE /api/v1/suppressions/:id`. The gate normalises addresses (case-fold, trim) so `Alice@Example.com` and `alice@example.com` resolve to the same row. Auto-suppression on bounces is wired by #24. See [docs/suppressions.md](docs/suppressions.md). (#25)

### Changed

- `EmailStatus` now includes `bounced`, surfaced via the `?status=bounced` filter on `GET /api/v1/emails`. The semantics: `sent` = the recipient's MX accepted the SMTP transaction; `bounced` = it accepted, then later returned a DSN; `failed` = we never reached an MX. (#24)

### Security

- **Breaking: DKIM private keys are now encrypted at rest.** Every `domains.dkim_private_key` is encrypted with AES-256-GCM using a new required `DKIM_ENCRYPTION_KEY` env var (32 bytes, base64). Stored as `v1:<iv>:<ciphertext>:<auth-tag>`. A DB dump without the env key leaks no signing material. Operators must add `DKIM_ENCRYPTION_KEY=$(openssl rand -base64 32)` to `.env` **before** pulling this version: boot fails loudly if it's missing or not 32 bytes. Existing rows are auto-encrypted on first boot via [src/db/encrypt-domain-keys.ts](src/db/encrypt-domain-keys.ts) (idempotent: already-encrypted rows are skipped on subsequent restarts). Rotation is documented in `SECURITY.md`. Decrypt failure at send time is fail-open (logs an error and sends unsigned) so a key-rotation accident can't take down outbound delivery. (#23)

### Fixed

- Email queue now resolves DKIM keys + `List-Unsubscribe` overrides via the email's `domainId` FK rather than parsing the sender domain out of `fromAddress`. The string-parse path was a correctness hazard for renamed domains and inconsistent with the schema's stamped FK. Falls back to a name-based lookup only when `domainId` is null (legacy rows from before the FK existed). Adds a unit test covering both paths. (#32)

### Changed

- **Runtime image no longer ships `drizzle-kit`.** Replaced `drizzle-kit migrate` at container start with a 60-line Bun-native runner (`src/db/migrate.ts`) that reads the committed `drizzle/<n>_*.sql` files and tracks applied tags in a new `__bunmail_migrations` table. Eliminates esbuild's bundled Go binary from the production image, closing ~36 Go-stdlib false-positive findings on Trivy's image scan. Existing `db:push`-provisioned databases are auto-baselined on first run (every known migration is recorded as applied without re-running its DDL). The Dockerfile is now multi-stage (install → prod-deps → run) so dev deps never reach the final layer; the run stage also applies the latest Debian security patches at build time. Migrations are now committed to `drizzle/` and removed from `.gitignore`. (#56)

### Security

- Bumped transitive deps via `package.json` `overrides` to close real medium-severity npm CVEs surfaced by the new image scan: `yaml@^2.8.4`, `file-type@^22.0.1`, `brace-expansion@^5.0.5`, `picomatch@^4.0.4`. `file-type` was promoted from a peer to a direct dep so the override applies. (#56)
