- **Inbound STARTTLS, submission STARTTLS and `MAIL_SOURCE_IP`, on Bun 1.4.4 and later (#414).** Bun 1.3.14 could not upgrade an accepted socket to TLS on the server side and ignored `localAddress` on outgoing sockets; Bun fixed both upstream (oven-sh/bun#31155, first released in 1.4.0) and BunMail verified them on 1.4.4 (openssl `s_client -starttls smtp` and nodemailer clients, no socket left behind after a hang-up at any stage, macOS and Linux). Every new setting is off by default and refuses to boot on a Bun older than 1.4.4 instead of silently not working, so existing deployments are unchanged. `SMTP_TLS_CERT` / `SMTP_TLS_KEY` make the inbound receiver offer opportunistic STARTTLS on port 25 (never required, AUTH stays off); a client's TLS error (a failed handshake or a broken record later) is one `warn` line (`Inbound SMTP TLS error`, with the IP, the TLS error code and `starttls`; submission logs `SMTP submission TLS error`), the start line carries `starttls`, and every `SMTP session closed` line (inbound and submission) now carries `secure`. `SMTP_SUBMISSION_TLS_MODE=starttls`, refused at boot on Bun until now, offers STARTTLS on port 587 (AUTH before it gets `538`; implicit TLS on 465 stays the default with a cert). `MAIL_SOURCE_IP` (one IPv4 and/or one IPv6 address) binds every outbound SMTP connection to the address of the MX address's family, shown on the session span as `network.local.address`; an address mail cannot leave from (loopback, link-local, multicast, broadcast, IPv4-mapped) refuses to boot, and the boot warns when it is on no interface or differs from `MAIL_PUBLIC_IP`. STARTTLS on 587 keeps the key off the wire only for clients that require it (AUTH is advertised before TLS), so implicit TLS on 465 stays the recommendation off trusted networks. Serving an MTA-STS policy for inbound mail and receiving TLS reports remain follow-ups.
