- **Dashboard flash banners show only BunMail's own messages (#421).** A redirect after a form action carried the banner's text in the URL (`?flash=<text>&flashType=error`), and the page showed any text it was given, so a phishing link such as `/dashboard/account/sso?flash=Your account was compromised, call ...` displayed attacker-written words inside the real dashboard (escaped, so no XSS; Info). Redirects now carry a **flash code** from a fixed, typed set (`?flash=webhook_not_found`), and the page shows only the message and colour written for that code in `src/pages/lib/flash-codes.ts`; an unknown code, or any other text, shows no banner. `flashType` is gone (the code decides the colour). A message that needs a value takes one non-negative integer, `?flashN=<digits>` and nothing else (an email count, a webhook or recipient limit, the unverified sender-domain records as bits). What used to be spliced into a flash is now a fixed sentence or one code per variant: the SSO provider's label (`Single sign-on account linked.`, `The sign-in provider could not be reached.`), the suppressed address, the passkey name problem, the domain verification marks (the domain page shows each record's status) and the message of a typed error (the sender domain, a DKIM rotation's detail); this also keeps suppressed addresses out of browser history and proxy logs. A webhook URL the SSRF guard refuses gets its own fixed message. The errors whose message used to be shown (template create and update, webhook create, DKIM rotation refusals) are now logged instead: typed refusals at `warn` with their class or code, anything else at `error`. **Upgrade note:** a bookmarked dashboard URL with an old free-text `flash` simply shows no banner. Docs: `docs/dashboard.md` (new Flash messages section), `ARCHITECTURE.md`.
