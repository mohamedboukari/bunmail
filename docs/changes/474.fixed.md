- **A database error while preparing a send no longer fails the email for good (#474).** The queue treated every error thrown before a send reached an MX host (the domain lookup, the suppression re-check before a retry, the attachments load) as an input error, so a connection reset, a serialization failure or an exhausted pool marked the email `failed` with `email.failed`. Only an input error (no valid recipients after parsing, an attachment no longer stored, now raised as `UnsendableEmailError`) still fails at once. A database or connection error (SQLSTATE class `08`, `40`, `53`, `57` or `55P03`, a Bun SQL connection or timeout code, a socket error) and any unexpected error now put the email back to `queued` on the normal retry backoff, the attempt counted, `last_error` holding the sanitized text and no webhook, logged at `warn` (`error` for an unexpected one); past `MAIL_RETRY_MAX_AGE_HOURS` it fails with `email.failed` as before.
